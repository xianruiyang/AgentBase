# 因果分析与差距证据

## 因果边界

- 把期望动作取决于故障原因、反复失效、系统机制、职责边界、架构、流程或上游判断的工作视为因果任务；不得把它伪装成单文件或旧测试维护。

## 认识状态

只为会改变方案、动作或完成结论的判断维护状态：

- `未知`：证据不足。
- `假设`：存在待反证解释。
- `局部证据`：证据只覆盖声明的一部分。
- `已推翻`：存在有效反例。
- `已验证`：沿用适用 `AGENTS.md` 的证据定义。

在关键判断升级为已验证前，主动寻找反例并使用不预设该判断成立的证据。由同一未验证判断导出的实现、文档、计划或检查不得充当独立验证。

## 分析准入

1. 先写清目标结果、关键判断、当前状态和能够推翻各假设的证据；不影响选择的未知项不纳入前置条件。
2. 确认授权范围内最接近已确认原因且可以改变的层；更上游但不可控的原因只作为边界，不用下游兼容静默吸收。
3. 修复方案需要证明错误机制已经改变时，同时读取 [verification-and-gates.md](verification-and-gates.md)，不要在分析阶段把拟议实现当作验证。
4. 新证据推翻上游判断时，记录直接反例并按全局失效熔断返回最早失效层。

已确认原因属于长期 owner 或共享契约时，从实际消费者反向确认仍复制、绕过或缓存该决定的路径；单个调用点不再触发错误不能证明同一机制已在其他适用路径消失。

## 规则执行失效定位

受支持场景出现本可预防的模型错误时，用同一次失败的直接证据区分最早失效层；后续层未被实际到达时保持未知，不因规则正文存在而跳过：

1. `definition_missing`：适用规则或能力合同没有覆盖该判断。以权威规则与需求的直接对照证明，修正其唯一规范 owner。
2. `route_or_reference_missing`：合同存在，但本次没有选择对应 skill、读取必要引用或进入正式动作入口。以实际路由、引用和入口 trace 证明，修正触发边界或入口连接。
3. `action_noncompliant`：规则与必要引用已经进入本次上下文，模型动作仍违反它。以实际可见输入、动作序列和反例证明，修正可执行指引、反馈或行为验证，不复制同义规则免责。
4. `state_writeback_missing`：动作本身符合合同且产生有效新证据，但所属方案、任务 state 或结果 owner 没有及时记录新的证据前沿与下一动作。以 state revision、结果收据和实际提交边界证明，恢复唯一写入口并检查依赖陈旧状态的后续范围。

四层可以在不同执行片段分别失效，但不得用后一层猜测替代未观察的前一层。结构有效的下一 revision 结果未被 state 引用，只直接支持第四层的写回漂移；它不证明结果语义正确。定位后把修复放回该层的 owner，并用原场景、同类变体和相近非触发场景验证机制，而不是为每个表象追加规则。

## 差距分析

- 按独立契约项维护目标、当前事实、直接证据、证据上限，以及符合、部分符合、缺失、冲突或未知状态。
- 只有目标语义、证据和状态相同的条款才合并；未检查项保持未知。
- 清单未覆盖用户请求范围时不得声称分析完成；因授权或证据缩小范围时明确说明。
- 先正向检查目标是否被完整覆盖，再反向检查每个动作是否有权威来源；不得由任务、旧测试或当前实现反推需求。
- 把差距事实、根因判断、方案和任务计划分层表达，不让它们互相充当证据。

## 局部修复

用户明确只授权局部修复或降低追溯深度时，缩小实施范围，同时说明仍保留的上游原因、复发条件和结论边界；不得把局部修复称为根治。
