# 证据前沿与纵向消费者

## 证据前沿

当前证据前沿是结果因果路径上最早满足以下条件的判断：它尚无直接适用证据，且成立与否会改变多个后续动作、方案选择或完成结论。只影响一个局部、可以直接完成和验证的未知项不因此升级为共享前提。

按以下顺序确定前沿：

1. 从当前用户可观察结果反向列出必要消费者和直接依赖。
2. 区分已经由实际消费者验证、只由生产者或替身自证、以及仍未知的判断。
3. 选择最靠近上游且会支配当前多个动作的未证判断，而不是最容易修改或已有文件最多的组件。
4. 预先写清能够推翻它的观察；无法改变当前动作的证据不进入前置调查。

## 最小纵向路径

纵向路径必须经过当前结果所需的实际消费者并产生可以直接验收的结果。建立模块、生成配置、单元测试通过、文档齐全或任务标记完成都不能替代消费者行为。

多个消费者共享未证前提时：

```text
证明共同前提
└─ 首个真实消费者结果
   ├─ 其余消费者 A
   ├─ 其余消费者 B
   └─ 其余消费者 N
```

### 活动切片锁

在修改两个以上平级消费者的生产代码、fixture、示例或测试前，先在当前执行上下文锁定：适用的公共合同与 owner、一个活动消费者、该消费者能够观察真实结果的 oracle、暂缓的平级范围，以及“当前消费者闭合”或“证据推翻上游”两类解除条件。该锁只是当前动作裁决；需要跨轮或多人恢复时写入既有执行检查点，不新增状态源。

- 公共合同或 oracle 仍有多个会改变实现的解释时，先回到相应 owner；旧测试结构不能替代合同裁决。
- 活动消费者未闭合前不切换到平级消费者，也不把多个尚未闭环的消费者绑定为一个实现或验证批次。
- 当前切片出现反例时只解除被证据推翻的锁并返回最早失效层；普通局部失败不借机横向展开。
- “已修改很多文件”“已经铺好测试”或“多个分支同时进行”不构成进展；可报告的执行进展是正式消费者闭环和支配未知的消除。

- 用户要求的批量数量决定最终覆盖范围，不自动取消这条依赖顺序。
- 首个消费者应以最小完整成本代表共享路径；不能为了便宜选择绕过关键机制的替身。
- 共同前提成立但首个消费者失败时，只修正该消费者直接覆盖的机制；不得把前提重新宣称为未知，除非新证据实际推翻它。
- 首个消费者成立后才能并行或批量扩展；扩展仍保留各消费者自己的差异验证。

纵向路径是既定设计下的执行顺序，不是用首个 case 演化设计。首个正式可用结果切片应按设计中的共享职责与消费者差异，深度优先完成其跨层生产内容、真实消费者和有效 oracle；只缩小同时展开的结果数量与证据成本，不缩减正式实现，也不允许用一次性 mock、绕过正式 owner 的硬编码或偏离既定契约的临时入口冒充闭环。其他结果随后仍按原设计、共享职责与依赖实现，不因首个结果形成新的架构继承关系。上游设计、职责或正式入口仍未确认时先交给 `$delivery-workflow` 或 `$change-governance`，不在执行切片中隐式决定。

实现、fixture、示例和测试代码都会固化当前判断并产生维护成本，因此同属扩量。首个切片成立前，只编写其实现与直接验收所需的测试；把最终矩阵先写完、把全部组合塞进参数化循环，或先为平级类型建设 fixture，都不属于纵向准备。

## 验证维度与结论边界

同一能力声明可能因载体、模式、状态、版本、revision、持久化或其他领域边界而改变行为或 oracle 时，在选择首个消费者前列出实际会改变结论的维度与等价依据。选择能够区分当前候选机制的最小组合，不机械展开完整笛卡尔积；未选择的组合只有得到直接证据或已验证等价关系时才进入覆盖范围。

组合开始扩量前形成紧凑的 coverage basis；它是当前执行裁决，不是新的状态源：

```text
claim:        本轮要证明的能力声明
dimensions:   改变机制、oracle、生命周期或边界的维度
equivalence:  可合并取值及其组件契约、接缝或结构证据
interactions: 共享分派、状态、持久化或其他真实耦合
cases:        代表 case 及各自新增的判别信息
promotion:    触发更高阶组合或穷举的反例与剩余未知
```

- 只改变已由组件契约、属性或边界测试覆盖的数据，不自动形成新的端到端组合；只看名称相似、同一接口或同一代码路径也不能单独证明运行等价。
- 覆盖可以由组件契约、接口接缝、一个真实纵向消费者、交互关系的代表 case 和既有缺陷回归共同组成；每项只证明自己的契约，组合结论必须保留所依赖的等价证据。
- pairwise 只在证据表明故障机制最多涉及两个维度时证明相应交互；否则它只是取样。共享状态或 oracle 涉及更高阶维度时，只升级对应交互，不把无关维度一起展开。
- 只有目标明确要求逐组合认证、组合闭集很小且成本低，或高后果交互无法取得充分等价证据时才穷举。owner、契约、oracle 均明确且无共享未知的小而廉价闭集直接走局部快速路径，不为它建立单独的 coverage basis；不得设置跨项目固定 case 数量。其他候选 case 不能新增判别信息时合并或删除。

任务合同保存需要裁决的维度和需要跨轮消费的 coverage basis，当前执行检查点保存本次消费者的实际 case，结果只声明直接验证覆盖的维度值或具有可复核依据的等价类。fixture、单一载体、单一模式或 pairwise 通过不得外推到未覆盖的高阶交互；反例只推翻其直接覆盖的共同前提和依赖结论。

## 持久任务投影

需要长期任务表时，由 `$delivery-workflow` 把证明动作和首个消费者结果投影为真实任务，并让依赖它们的横向任务消费明确产出。`$task-table-manager` 只保存这些关系，不用深度、顺序号或完成数量重新推断前沿。

证明任务没有可复核产出，或横向任务实际上不消费其结果时，说明依赖设计仍未成立，应返回方案层重裁，而不是建立形式化门禁。
