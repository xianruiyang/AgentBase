# 证据前沿与纵向消费者

## 证据前沿

当前证据前沿是结果因果路径上最早满足以下条件的判断：它尚无直接适用证据，且成立与否会改变多个后续动作、方案选择或完成结论。只影响一个局部、可以直接完成和验证的未知项不因此升级为共享前提。

按以下顺序确定前沿：

1. 从当前用户可观察结果反向列出必要消费者和直接依赖。
2. 区分已经由实际消费者验证、只由生产者或替身自证、以及仍未知的判断。
3. 选择最靠近上游且会支配当前多个动作的未证判断，而不是最容易修改或已有文件最多的组件。
4. 预先写清能够推翻它的观察；无法改变当前动作的证据不进入前置调查。

## 最小纵向路径

纵向路径必须经过当前结果所需的实际消费者并产生可以直接验收的结果。建立模块、生成配置、单元测试通过、文档齐全或任务标记完成都不能替代消费者行为。

多个消费者共享未证前提时：

```text
证明共同前提
└─ 首个真实消费者结果
   ├─ 其余消费者 A
   ├─ 其余消费者 B
   └─ 其余消费者 N
```

- 用户要求的批量数量决定最终覆盖范围，不自动取消这条依赖顺序。
- 首个消费者应以最小完整成本代表共享路径；不能为了便宜选择绕过关键机制的替身。
- 共同前提成立但首个消费者失败时，只修正该消费者直接覆盖的机制；不得把前提重新宣称为未知，除非新证据实际推翻它。
- 首个消费者成立后才能并行或批量扩展；扩展仍保留各消费者自己的差异验证。

## 持久任务投影

需要长期任务表时，由 `$delivery-workflow` 把证明动作和首个消费者结果投影为真实任务，并让依赖它们的横向任务消费明确产出。`$task-table-manager` 只保存这些关系，不用深度、顺序号或完成数量重新推断前沿。

证明任务没有可复核产出，或横向任务实际上不消费其结果时，说明依赖设计仍未成立，应返回方案层重裁，而不是建立形式化门禁。
