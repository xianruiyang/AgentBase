# C++ 架构与编译依赖

先确认项目自己的模块边界、构建系统和框架合同，再应用本 skill；不要用通用 include 规则覆盖项目明确要求。

## 维护职责与模块边界

1. 修改前确认相关模块的职责、依赖方向、公开入口和实际调用方，把行为放入已有的正确 owner。
2. 不为局部便利建立平行实现、反向依赖、跨层直连或新的权威入口；include 暴露依赖倒置时，先修正职责或接口边界。
3. 修改公共接口、公共头文件或模块依赖前检查直接消费者，优先缩小公开面和依赖传播范围。
4. 不以减少 include 或文件数量为由破坏清晰职责；持续增长的公共头、依赖环和反向模块依赖应作为边界问题处理。

## 组织 Include 与完整类型

1. 让公共和可复用头文件自包含，直接包含其公开声明真正需要的正式头文件；PCH、unity 或传递包含偶然提供的可见性不构成头文件合同。
2. 公共头文件只引入布局、继承、按值成员、inline、模板实例化或宏展开确实需要的完整定义；仅使用指针或引用且语义允许时，使用安全的前置声明。
3. 不前置声明标准库实体，也不在基类、按值成员、要求完整类型的模板位置，或会在该点实例化析构、`sizeof`、成员访问的代码中强行使用不完整类型。
4. 把只服务于实现且不属于正式 PCH 合同的重型依赖移到源文件，并优先包含提供目标符号的最窄正式头文件。
5. 遵守框架规定的 include 顺序、生成头位置和模块可见性；删除或替换 include 前确认符号真实来源及受影响使用方。

## 使用 PCH 与 Unity Build

1. 把 PCH 和 unity build 视为正常的编译加速机制；遵循项目正式配置，没有测量证据时不主动禁用或削弱它们。
2. 只把稳定、解析成本高且多数翻译单元复用的头纳入 PCH；根据实际重建成本和编译计时调整，不按头文件数量判断。
3. 源文件可以依赖构建系统明确保证的 PCH 或框架聚合头合同，不必为形式完整机械重复这些正式依赖。
4. 每个源文件都不得依赖相邻源文件在 unity 拼接中偶然引入的声明、宏或内部实体；拼接分组与顺序变化不应改变语义。

## 验证改动

1. 使用项目正式的 PCH 与 unity 配置构建直接受影响目标；公共头或模块边界变化时继续构建必要消费者。
2. 项目已有单翻译单元、非 unity、无强制 PCH 或 include-hygiene 入口时，把它们作为发现偶然依赖的补充诊断，不把诊断配置替代为生产默认值。
3. 只有构建计时或依赖数据直接支持时才声称编译性能改善；include 数量减少本身不是性能证据。
