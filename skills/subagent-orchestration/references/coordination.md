# 成本与交接控制

## 是否委派

用户明确不使用子代理时不进入委派。用户明确要求使用时，该要求允许主代理选择合适角色，但不扩大原任务的操作和外部影响授权；子问题无法安全分离时不为满足形式而强行拆分。

用户未指定时，以下条件同时成立则默认委派：取证或试路结果是后续决策的必要输入；子问题有独立输入、输出和停止边界；结果能让主代理减少读取、搜索或试错；交接、复核和返工成本低于预计节省；子代理失败不会扩大授权或污染生产状态。任意一项不成立，或任务很短、结果高度依赖主代理持续判断、双方必然重复读取同一上下文、正式实现本身才是主要工作时，主代理直接完成。

## 协作拓扑

```text
主代理目标与授权
├─ evidence：只读取证
│  └─ 主代理逐项接纳 F/X/N/U
├─ experiment：只消费已接纳证据与待判假设
│  └─ 主代理裁决可行路径
└─ 主代理：正式设计、实现、验证、状态、Git、发布与完成
```

默认串行使用最小链路。用户要求并行，或用户未指定且至少两个子问题各自满足默认委派条件时，只有它们相互独立、没有共享未证前提、不会触碰同一状态、各自结果不决定对方输入且并发净收益成立时才优先并行；主代理继续的本地工作也不得与子代理重复。子代理不得再生成后代代理。

派发时使用最小 capsule，不默认继承整段对话；引用稳定文件、ID 或快照，避免复制原文。跟进消息只传递新的目标修正、已接纳证据 ID 或反例；无需改变任务时等待结果，不通过反复催促制造重复输出。

主代理接收后先检查身份、范围、快照、直接引用、反例和未知，再决定接纳、补证、转入实验或停止。任何子代理的“完成、全部、唯一、无问题”都只是待审主张；只有主代理复核且实际消费者证据覆盖后才能进入完成结论。
