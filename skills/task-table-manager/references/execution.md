# 任务执行与恢复

## 选择当前工作

1. 直接从任务文档与当前证据选择工作；任务较多时可用 `taskctl next` 取得有界候选和诊断。
2. 需要压缩执行上下文时用 `taskctl context --capture --id <ID>` 读取任务合同、直接依赖结果、必要上游和直接下游；工具在最终模型投影后捕获实际可见来源。模型结果文件只写语义正文，完成时绑定实际执行的任务合同与来源；收据及参数按 [执行命令合同](execution-tooling.md#完成写入) 处理。不完整时先按返回 ID 补齐并重新捕获，不在完成时用当前版本代替。
3. 稳定上游的单一候选可按用户优先级和真实依赖执行；多个候选共享未证前提、昂贵验证、反复失效或并行冲突时，把候选与依赖证据交给 `$execution-governor` 裁决当前证据前沿和首个消费者。
4. 选择依据是任务完成后能否形成有用结果与直接证据，而不是图上层级、数值深度、任务数量或 CLI 排序。风险取证、用户裁决和共享前置可先行；`taskctl next` 不计算闭环优先级，也不决定执行许可。
5. 取得消费者结果后，有交付链时把证据回流到 `$delivery-workflow` 的所属上游；独立任务对照用户要求和合同记录直接证据。证据前沿、消费者、验证 case、最近证据、失效来源或下一动作改变且需要跨轮恢复时，先以 `note` 更新执行检查点。证据推翻上游时先停止依赖动作、写回并返回最早失效处；命中 `$execution-governor` 条件时由它控制该过程。需要改变用户确认目标时交由用户裁决，有交付链则按 `DCR` 保留待议变更。
6. 有效规划要求目标、所选方案、关键依赖与风险、预期结果和验证方式足以安全执行，不要求先穷尽全部细节。若任务合同仍不足，修订最早缺失的阶段产物或任务合同，不创建占位结果。

## 状态

```text
todo → claimed → in_progress → review → done
                   ↘ blocked
任意状态 → retired
```

- 上图是默认表达，不是 CLI 强制状态机。非典型流转或文档定义的扩展状态会原样保存并返回诊断，但不代替模型根据真实工作作出判断。
- `claim` 记录 owner 意图；不同任务可以并行领取。owner 不一致是协调诊断；每次状态写入都必须基于调用方刚读到的 state revision，缺少或冲突才阻断写入。
- `start` 表示开始实际工作。
- CLI 在 `start` 或状态首次进入 `in_progress` 时记录 `started_at`，在任务进入 `done/retired` 时记录 `ended_at`；两者均为 UTC RFC3339 秒级机器字段。重开或其他离开终态的转换清空 `ended_at`，同一任务第一次实际开始时间继续保留。
- `note` 更新简短进度、阻塞原因、下一动作或结构化执行检查点，不保存运行日志；检查点只保存当前前沿、消费者、验证 case、最近有效结果或关键反例和失效来源，原始尝试仍留在日志或证据 owner。
- 非空阻塞原因默认把任务表达为 `blocked`；原因与状态不一致时报告诊断并保留信息，不为了形式一致丢失原始记录。
- `complete` 记录模型已经做出的完成判断；从 `todo/claimed/blocked/done` 等非典型状态调用时返回诊断。语义结果可结构化但缺收据、覆盖不完整或来源陈旧时不由 CLI 拒绝；显式收据缺失、不可读或身份不一致时无法形成所声明的永久引用，写入前拒绝并保持结果与状态不变。
- `reopen` 和 `release` 分别记录完成结论失效与领取结束；对当前状态或 owner 的不一致返回诊断。
- `retired` 用于上游方案变化、任务被替代或不再属于当前范围；保留原合同、结果和退出原因。

CLI 对已有合同和状态写入统一使用 CAS：先读取当前记录，再把其 revision 作为对应 `--expected-*-revision` 传回；`complete` 同时要求 task 与 state revision，分别绑定执行合同和保护状态写入。缺少或冲突都会拒绝本次写入。CAS 只防止版本错绑与并发覆盖，不证明 owner、流转或工作内容正确。owner 不一致和不同任务的 mutation scope 重叠都只返回协调诊断。

## 并行与下游消费

- `hard` 依赖完成前，下游仍可做不消费其结果的分析、取证或准备，但不得假装前置产出已经成立。
- 公共产出与消费者接入分成任务时，消费者通过 `dependencies[].consumes` 指出实际使用的产出；建立但无人消费的公共层不是完成结果。
- 完成任务时把后继真正需要的结论写进 `outputs`；原始日志、截图和大型文件保存在项目适合的位置，只登记路径和简要用途。
- `context` 加载直接依赖结果和任务来源的传递语义祖先，并返回直接下游；需要完整后继影响时使用递归 `impact`，再从实际系统补齐任务图未登记的消费者。
- 新证据推翻上游设计或方案时，先停止依赖动作并记录失效来源；已有稳定来源 ID 时写入 `invalidated_source_ids`。有交付链则回到 `$delivery-workflow` 修订，独立任务返回其要求或合同；命中 `$execution-governor` 条件时由它控制执行。CLI 不批量重置任务。
- 上游修订后逐项判断递归后继任务与既有结果：仍有效的重新验证，需要修改的更新或重开，被替代的退休；快照资产缺失、损坏、覆盖不完整或逐来源陈旧的结果不能直接沿用为当前证据。
- 重新执行或验证后提交的新结果只按自身 `evidence_for`、执行时捕获的 `source_snapshot_ref` 和直接验证覆盖当前目标；依赖、消费或同一候选集合不自动扩大覆盖。旧结果继续显示其原诊断，模型不得因为存在后继结果而忽略未被新证据明确覆盖的目标。

## 推理与领域 skill

任务的 `reasoning_hint` 和 `suggested_skills` 只帮助开始工作，不授权查询或改变线程推理深度。仅在用户明确要求时使用 `$reasoning-governor`；领域 skill 仍按修改对象触发，不受任务文件固定。

## 进度报告

`taskctl status` 固定返回所有任务状态数量，并可读取交付链索引中的上游未决数量以及结果验证摘要。结果摘要分别命名当前状态引用结果、任务合同 revision 陈旧结果、含来源快照问题的结果、含诊断结果及诊断条目，不用“当前”或“陈旧”的无作用域名称代替。报告时说明：

- 哪些任务完成、进行、评审、阻塞或待办；
- 哪些关键上游条目仍为 open/unknown；
- 多少结果包含验证，哪些仍有未决问题。

这些指标互不替代，不合成误导性的总体百分比。

最终复核按 [完成标准](../SKILL.md#完成标准) 区分交付链与独立任务。有交付链时核对当前确认的 Markdown 目标、约束与全部 DCR；范围较大可运行 `completion-context`，分页与快照恢复只按 [复核命令合同](completion-tooling.md#分页与快照) 执行。本次方案改变长期 owner 或契约时还要复核递归影响中的适用消费者和结果来源时效；任务全部 `done`、结果带验证或中间阶段审核通过，都不能单独得出整体完成。
