## 职责

任务表只记录下一步、依赖、产出、验收、初始思考深度建议、进度和回退边界。执行正文、长证据、raw JSON、截图清单和日志放入任务产物目录。

## 任务项准入：禁止形式主义

任务表用于执行已经确定的方案，不用于再次设计方案。一个条目只有同时满足以下
条件才可以成为任务：

1. 完成后产生实际结果，例如删除/归档有害资产、增加测试、修改实现、迁移能力、
   完成定向验证，或交付用户明确要求且会被后续实现直接使用的分析清单。
2. 结果可由文件、代码、测试、运行状态或明确清单直接验收，且证据范围与任务
   声称交付的范围一致；编译、结构、mock、recording 或 synthetic 结果不能扩大
   解释为真实集成或生产行为。
3. 直接依赖、共享基础能力和验收路径已经明确；不得用狭窄名称包装尚未规划的
   公共架构、跨模块基础设施或多个独立生命周期。
4. 该工作不能完整并入相邻任务的依赖、执行步骤或验收标准。

删除某一行不会导致缺少交付物、状态变化或必要验证时，必须删除或合并该行。
任务名称使用“具体动作 + 具体对象”，不得只写抽象管理名词。

### 设计与任务表的边界

- 架构、功能范围、模块分工、唯一 owner 和源码依赖必须先在设计文档中确定，再
  编写执行任务表。
- 设计已经存在时，不得设置“确定/固定/完善/冻结设计、模块、owner、DAG”任务。
- 设计尚未完成时，先完成设计文档；不得用一个未来的“设计任务”掩盖执行表缺少
  前提。
- 执行中发现真实设计缺口时，停止受影响任务并修正设计和依赖；不得预防性加入
  大量“复核设计”任务。
- 评审或执行准备中发现叶子任务依赖未实现的公共接口、共享 production seam 或
  新的跨模块职责时，修正依赖或拆出具有实际产出的前置任务；不得把新增范围静默
  吸收到原任务并维持原名称、进度和验收。

### 不得单独成任务的管理动作

以下内容默认写入任务表结构、依赖、memo、handoff 或相邻任务步骤，不得单独
占用任务 ID：

- 创建、填充、生成、冻结或复核任务表/子任务表；
- 编排任务、选择下一任务、更新进度或记录 source/build identity；
- 为已有设计再次建立 capability map、owner map 或依赖图；
- 准备 handoff、memo、`deps_for`、receipt 或 Gate 名称；
- 没有用户交付或行为验收要求的 readiness、同步状态检查和重复审计；
- 在前一阶段已经完成的资产映射，在后一阶段无实际变化地再次刷新或复核。

子表必须在编写任务表时直接写好。主表可以保留“完成某子表”的父任务行，以承载
进入条件、进度和回写关系，但不得再增加“生成、冻结、复核或编排子表”的任务。

### 有害旧资产的处理

- 对已经确认有害且无价值的旧测试、加载入口、selector 和 Gate，直接删除。
- 可能复用的内容先退出构建、加载、发现、默认选择和 Gate，再归档或交给具体
  新模块任务整理。
- 不得为了删除有害旧测试，再为这些旧测试编写“隔离测试”。
- 只有某个严重问题容易复发时，才为替代后的新行为补一个低成本回归测试；该测试
  属于新模块的测试任务，不单独建立“有害资产测试”阶段。

### 可成立的分析或检查任务

分析、清点或审计只有在结果直接驱动后续修改时才能单独成任务，且必须明确：

- 输出哪份具体清单或决策；
- 每一项由哪个后续任务消费；
- 完成后会删除、修改、复用或阻断什么。

纯“了解、确认、复核、统一口径”而没有直接消费者和状态变化的内容不得成为任务。

### 改写示例

| 不合格任务 | 正确处理 |
| --- | --- |
| 固定 capability、模块、owner 与 DAG | 先在设计文档中确定；任务表从“按既定设计清点并分配现有代码”开始 |
| 建立有害 loading/selector/Gate 的隔离测试 | 直接删除或归档有害入口；新 selector/Gate 的测试放入新 TestInfrastructure 测试任务 |
| 填充并冻结六个子表 | 编写任务表时直接写好子表，不创建任务 |
| P6 再次刷新迁移矩阵 | 当前资产变化时更新对应任务输入，不设置重复复核任务 |
| 编排子表 | 父任务直接写“完成某子表”，只承担进入条件、进度和回写 |
| 执行 readiness | 仅在用户明确要求 readiness 且结果本身是交付物时保留 |

## 任务落点

- 在 `docs/plan/` 下新建唯一任务根目录，格式为 `<YYYYMMDD>_<NAME>/`。
- `YYYYMMDD` 使用创建任务时的 8 位数字日期；`NAME` 使用简短、稳定、可读的任务名。
- 主任务表、子任务表、`<任务表名称>_tempFiles/` 及所有任务相关内容都放在该任务根目录内，不散落到其他目录。
- 若用户未指定主表文件名，默认使用 `<NAME>_TASK_TABLE.md`。
- 任务表中的同计划内部引用以当前计划目录为根使用相对路径，例如 `<NAME>_TASK_TABLE_tempFiles/P1-001/handoff.md`；不写 `docs/plan/<YYYYMMDD>_<NAME>/...` 或对应绝对路径。
- 跨计划依赖使用 `docs/plan/...` 项目相对路径；项目外稳定依赖才保留必要的绝对路径。

示例：

```text
docs/plan/20260721_WATER_SYSTEM/
├── WATER_SYSTEM_TASK_TABLE.md
└── WATER_SYSTEM_TASK_TABLE_tempFiles/
```

## 三层依赖

### 任务表级

只放 90% 任务都需要的稳定规则或真源索引，写明读取条件，不放中间产物。

### 任务组级

只放该组 90% 任务都需要的阶段规则、门禁和上游部分依赖。组内共享中间结论登记到 `<artifact_root>/<组ID>/memo.md`。

### 任务项级

只放当前项需要的：

- 必要前置任务 ID。
- 上游为当前项生成的 `deps_for/<当前任务ID>.md`。
- 当前项独有的小型规则、命令、截图或摘要。

不得直接依赖上游完整产物、无关任务组或未来资料。

上游任务的 `done` 只提供其验收标准已经直接证明的产物和能力；下游不得仅根据
状态推断更强的生产可用性、真实集成或未写明的行为保证。

## 必需字段

| 字段 | 要求 |
| --- | --- |
| `ID` | 稳定编号，后续引用不得改名 |
| `任务名称` | 简短说明动作 |
| `依赖` | 三层必要依赖和专属 `deps_for` |
| `目标产出` | 可交付结果，不写产物正文 |
| `验收标准` | 可执行、可判断，证据直接覆盖任务声称交付的结果 |
| `思考深度` | 初始建议：`low/medium/high/xhigh/max/ultra`；执行时按 `SKILL.md` 动态判断 |
| `完成进度` | `todo/in_progress/review/done/blocked + 百分比`；嵌套表注明统计层级 |
| `产物路径` | 正式产物或任务目录；未完成可空 |
| `回退目标` | 仅根因已明确来自上游时填写；否则留空 |

## 思考深度初始分配

- 取足以完成任务的最低等级。
- 确定性命令、脚手架、打包、整理用 `low`。
- 明确契约下的常规实现与测试默认 `medium`。
- 未公开协议、跨模块竞态、高风险写入或关键门禁可用 `high`。
- `xhigh` 只用于错误代价高且状态关系确实复杂的任务。
- `max/ultra` 只用于当前运行面支持，且错误代价、状态关系和未决依赖同时极高的任务。
- 不得因任务长、步骤多或重要就预防性使用 `high/xhigh/max/ultra`。
- 本字段不是运行时锁定值；执行时遵守 `SKILL.md` 的动态调节规则。

```md
# <任务表名称>

## 任务表级依赖

| 依赖ID | 文件 | 用途 | 读取条件 |
| --- | --- | --- | --- |

## 当前状态

| 字段 | 值 |
| --- | --- |
| `status` | `todo/in_progress/done/blocked` |
| `current_task` | 当前任务 ID |
| `artifact_root` | `<任务表名称>_tempFiles/` |
| `active_child_table` | `none` 或活动子任务表链接 |

## 子任务表索引

| 子表ID | 父任务ID | 子任务表 | 完成进度 | 当前子任务 | 进入条件 | 完成后回写位置 |
| --- | --- | --- | --- | --- | --- | --- |

## 任务组

| 组ID | 任务范围 | 组目标 | 组级依赖 | 进入条件 |
| --- | --- | --- | --- | --- |
```

## 产物目录

必须建立：

```text
<任务表名称>_tempFiles/
├── README.md
├── <组ID>/memo.md
├── <任务ID>/
│   ├── handoff.md
│   ├── deps_for/
│   └── artifacts...
└── common/
```

每项只有一个人工交接入口 `handoff.md`，简明记录实际交付范围、有效验证、未覆盖
边界和下一任务的精确入口，不复制执行流水。面向不同消费者的依赖必须分别生成，
不共用“大摘要”。

## 子任务表

独立且复杂的新范围可以拆出子方案和子任务表。创建时必须：

1. 给子表分配稳定子表 ID 和独立 `artifact_root`。
2. 子表当前状态写入 `parent_table`、`parent_task`、`parent_child_index_id`、`parent_writeback`。
3. 主表“子任务表索引”登记可点击 Markdown 链接、进度、当前子任务、进入条件和回写位置。
4. 主表 `active_child_table` 指向活动子表。
5. 父任务行“依赖”字段登记同一链接。

不得只把子表路径写在对话、handoff 或 memo 中。

父表、子表和最终可执行叶子的进度不得混合计算。进度比值必须说明分母属于直接
子项、最终叶子还是能力覆盖；不得用已完成父级容器数量表示总体实现比例或掩盖
未完成叶子。

## 编写流程

1. 读取用户要求、必要真源和已有任务表。
2. 确认设计已经足以直接执行；不足时先补设计，不创建占位设计任务。
3. 从实际交付物和状态变化反推任务，执行“删除该行是否会缺少结果”的准入检查。
4. 确定 `docs/plan/<YYYYMMDD>_<NAME>/` 任务根目录、任务表名称与 `artifact_root`。
5. 写任务表级依赖。
6. 划分任务组和组级门禁。
7. 拆分稳定任务 ID，合并纯管理步骤和重复检查。
8. 填写九个必需字段，思考深度只给最低充分的初始建议，回退目标默认留空。
9. 规划候选消费者和跨组 `deps_for`。
10. 建立产物根目录、README 和组 memo。
11. 检查任务表不含形式任务、执行流水、大段方案正文或 raw 产物。

## 整理已有任务表

- 保留真实状态、验收摘要和正式产物链接。
- 把长证据、probe、registry、截图和日志移到任务目录。
- 把旧全局依赖重分为三层。
- 为后续消费者补专属 `deps_for`，为组内共享结论补 memo。
- 清除未经根因确认而机械预填的回退目标。
- 检查所有活动子表在主表中有链接和同步进度。
- 检查父级容器、最终叶子和能力覆盖是否被混为一个进度比值，并修正误导性完成
  口径。
- 删除或合并再次确定设计、生成/冻结/复核任务结构、重复映射、编排和纯状态记录
  等形式任务。
- 将“裁决、复核、统一口径”等含糊名称改为明确的删除、测试、实现、迁移或验证
  动作；无法改成实际动作的任务直接删除。

## 禁止

- 不让任务表同时承担计划、日志和产物仓库。
- 不把所有资料列成每轮必读。
- 不在依赖字段引用大型原始产物。
- 不机械填写上一项为回退目标。
- 不为预防性覆盖普遍分配 `high/xhigh/max/ultra`。
- 不把设计、任务表维护、进度记录或重复复核包装成执行任务。
- 不为清除有害旧测试再编写服务于旧测试的测试。
