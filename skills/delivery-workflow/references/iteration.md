# 阶段推进与反馈

## 建立链路

1. 先与用户商议并确认要求和授权，提取 `REQ/AC/CON`；把用户明确给出的设计单独写为 `UDES`。
2. 运行 `workctl protect` 固化需求和用户设计，再开始执行闭环。
3. 根据受保护结果建立模型 `DES`，确认职责与依赖足以指导现状比较。
4. 通过直接检查形成 `OBS`，再从 `REQ/AC/UDES/DES` 与 `OBS` 的差异形成 `GAP`。
5. 为每个适用 `GAP` 选择 `SOL`；方案动作必须能追溯到目标，不为已有实现制造工作。
6. 将未交付的 `SOL` 投影成任务，明确真实依赖和下游需要的产出。
7. 执行任务并写结果；只把证据覆盖的行为标为已验证。

阶段可以局部交错。可以先执行一个取证任务补充 `OBS`，也可以在实现中发现新事实后修订设计；不得为了保持线性外观而隐藏回退。

## 认识状态

- `confirmed`：由适用规范或直接证据支持，且适用范围明确。
- `proposed`：可供评审或实施选择，但尚未成为确定目标或设计。
- `open`：已有明确问题或选择，仍需输入或裁决。
- `unknown`：当前证据不足，不能可靠陈述。
- `superseded`：条目仍用于追溯，但已由明确 ID 替代。

状态由模型根据来源和证据判断。CLI 只统计与定位，不自动改变状态。

## 新证据处理

新证据出现时先判断目标是否受保护：

1. 若最早受影响对象是 `REQ/AC/CON/UDES`，不得修改；建立 `DCR`，说明证据和影响，并继续不依赖该变更的工作。
2. 若对象是 `DES/OBS/GAP/SOL/DEC`，修订该条目的正文、状态或关系。
3. 运行 `workctl impact` 查看引用它的下游对象。
4. 逐项判断下游是仍有效、需要更新、需要重做还是仅需重新验证。
5. 任务状态不自动回退；只有任务合同或完成结论实际失效时才重开相应任务。
6. 其余可完成内容结束后，汇总 `DCR` 与用户讨论；用户没有明确确认前不把建议写入受保护基线。

文件哈希变化、链接数量变化和索引刷新本身都不是语义失效证据。

## 进度表达

至少分开报告：

- 任务执行状态：待办、进行、评审、阻塞、完成。
- 上游认识状态：`open/unknown` 条目数量和关键 ID。
- 受保护基线状态和延后讨论项数量。
- 结果验证状态：有结果、有验证、仍含未决问题的任务数量。

不得把三者压成一个“总体完成百分比”。如果必须给出百分比，明确分母和它只代表哪一层。

## 最终复核

1. 从 `protected-baseline.json` 取得当前范围全部 `REQ/AC/UDES`，不得从任务表反推目标集合。
2. 先用 `workctl index` 重建当前索引，再使用 `taskctl completion-context`；保存首次返回的 snapshot ID，并随 `pagination` 游标传回。若快照改变，从第一页重审；否则遍历目标、约束、开放延后项及单目标候选任务，逐项检查证据是否直接覆盖目标对象、入口、范围和生命周期。
3. 检查 `CON` 约束以及所有 `deferred/open` 的 `DCR`。只要某项表明受保护目标尚未满足，就不能声明最终完成。
4. 只有全部需求和全部用户设计均成立时才报告当前范围完成。模型设计审核、现状审核、方案审核、任务完成率和 CLI 检查只能分别报告为中间阶段结果。

## 与专项 skill 协同

- 根因或职责入口判断由 `$change-governance` 提供方法，结论分别进入 `OBS/DES/SOL`。
- 代码结构、C++、空间、UE 等判断由对应 skill 产生证据或实现结果，交付链只保存引用和简要结论。
- `$task-table-manager` 返回的任务上下文应包含精确上游条目和前置结果，不要求执行者读取全部阶段文档。
- `$reasoning-governor` 只调节 active Goal 的 next-turn 深度，不写入任务状态或阶段文档。
