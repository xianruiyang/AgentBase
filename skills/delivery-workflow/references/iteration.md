# 阶段推进与反馈

## 建立链路

1. 先把用户表达与项目目标、直接证据、历史决策、受影响对象和长期后果对照，识别会改变结果的隐含需求、冲突与取舍；向用户说明洞察并共同校准要求、授权和验收，再提取 `REQ/AC/CON`，把用户明确给出的设计单独写为 `UDES`。
2. 在文档中保留用户确认来源；需要跨轮核对时可运行 `workctl protect` 记录快照元数据，但 CLI 不是进入执行闭环的前置许可。
3. 根据受保护结果建立模型 `DES`，确认权威职责、当前消费者、共同决定、边界差异与依赖方向足以指导现状比较。
4. 通过直接检查实际 owner、消费者、派生产物、绕过或复制路径形成 `OBS`，再从 `REQ/AC/UDES/DES` 与 `OBS` 的差异形成 `GAP`。
5. 为每个适用 `GAP` 选择 `SOL`；共享职责的方案覆盖 owner、当前消费者接入、旧同责路径退出和验证，动作必须能追溯到目标，不为已有实现或假设未来复用制造工作。
6. 将未交付的 `SOL` 投影成任务，明确真实依赖、消费内容、下游需要的产出，并使当前方案动作到最近可验证交付结果的纵向链与闭合位置可识别。
7. 在可执行候选中优先推进最接近纵向验证闭环的当前目标链；闭环后立即用实际结果与直接证据确认或修正方案、模型设计和需求达成判断。
8. 执行任务并写结果；只把证据覆盖的行为标为已验证。

阶段可以局部交错。可以先执行一个取证任务补充 `OBS`，也可以在实现中发现新事实后修订设计；不得为了保持线性外观而隐藏回退。

## 执行上下文

执行一个方案动作或任务前，默认形成以下最小语义闭包：

- 当前要交付或验证的目标；
- 直接支配该动作的 `SOL/GAP/DES/AC/REQ/UDES` 条目；
- 本动作真实消费的直接依赖结果及其执行时来源版本；
- 对当前对象、范围、授权、安全和验收适用的约束。

这组内容已能可靠确定动作、边界和验证时停止加载，不因工作区存在其他阶段、历史记录或平级任务而全量读取。出现以下任一情况时，继续取得能消除相应不确定性的关联证据：目标或来源仍有歧义；当前观察推翻上游；长期 owner、正式契约、权威状态或共享行为改变；实际消费者、派生产物或旧路径需要影响传播；进入最终完成复核。扩展仍按实际关系和证据需要进行，不使用固定 Token、调用次数、文档数量或图深度代替语义判断。

`taskctl context` 可以压缩提供任务、直接依赖结果、必要上游和来源快照；没有任务表时按同一闭包直接读取阶段文档。截断、缺项或陈旧来源只是继续精确取证的信号，CLI 不判断上下文已经充分。

## 纵向闭环推进

- 有效规划不是穷尽所有细节，而是当前目标、所选方案与设计、关键依赖与风险、预期闭环结果和验证方式已经明确到足以安全执行。
- 先按用户优先级、硬依赖、关键风险、共享前置、冲突和当前能力确定可执行候选；条件相当时，优先继续当前目标链直至最近的直接可验证结果，避免同时打开更多未闭合的平级分支。
- 风险取证或共享前置可以先行；不能产生有用结果或直接证据的深层叶子不是闭环。任务图深度只提供线索，不形成数值评分，也不让 CLI 决定优先级。
- 闭环证据应立即回流到 `SOL/DES` 和需求达成判断；证据推翻可变判断时回到最早失效条目，要求改变受保护 `REQ/AC/CON/UDES` 时建立 `DCR` 并交由用户裁决。

## 认识状态

- `confirmed`：由适用规范或直接证据支持，且适用范围明确。
- `proposed`：可供评审或实施选择，但尚未成为确定目标或设计。
- `open`：已有明确问题或选择，仍需输入或裁决。
- `unknown`：当前证据不足，不能可靠陈述。
- `superseded`：条目仍用于追溯，但已由明确 ID 替代。

状态由模型根据来源和证据判断。CLI 只统计与定位，不自动改变状态。

## 新证据处理

新证据出现时先判断目标是否受保护：

1. 若最早受影响对象是当前执行周期内已经用户确认的 `REQ/AC/CON/UDES`，不得自行修改；建立 `DCR`，说明证据和影响，并继续不依赖该变更的工作。CLI 报告的快照漂移只是这个判断的线索。
2. 若对象是 `DES/OBS/GAP/SOL/DEC`，在修改前保存当前显式下游及其关系；再修订该条目的正文、状态或关系。
3. 修改后运行 `workctl impact`，并从实际调用、数据、状态、生成和验证关系补齐工具无法发现的消费者与派生产物；以修改前后集合的并集作为待裁决范围，查询为空不证明没有影响，同时复核下游语义、范围、优先级和用户可观察结果是否仍对齐确认目标。
4. 逐项判断下游为仍有效、更新、迁移、退出、重做或重新验证，并把判断写回其所属阶段条目、任务合同、任务状态或结果；新发现的长期依赖补入正式关系，不只留在进度说明。
5. 重新投影受影响任务：合同或完成结论失效时更新或重开，被替代时退休，需要新产出时新建；CLI 不自动批量改变状态。
6. 检查工作实际依据的上游版本；来源版本未知或陈旧的结果不得沿用为当前证据，完成重新执行或验证后再提交新结果。
7. 其余可完成内容结束后，汇总 `DCR` 与用户讨论；用户没有明确确认前不把建议写入当前执行周期的确认文档。

文件哈希变化、链接数量变化和索引刷新本身都不是语义失效证据。

## 进度表达

至少分开报告：

- 任务执行状态：待办、进行、评审、阻塞、完成。
- 上游认识状态：`open/unknown` 条目数量和关键 ID。
- 当前用户确认范围、快照对齐状态和延后讨论项数量。
- 结果验证状态：有结果、有验证、仍含未决问题的任务数量。

不得把三者压成一个“总体完成百分比”。如果必须给出百分比，明确分母和它只代表哪一层。

`workctl render` 生成的 `WORK_STATUS.md` 是上述分层状态的低成本接手视图：它显示快照对齐情况、可修订语义未决、可读取的任务状态和结果统计。任务域部分无法读取时明确显示诊断，不伪装为零任务。该视图不产生 READY 或最终完成判定。

## 最终复核

1. 从当前执行周期经用户确认的 `requirements.md` 和 `user-design.md` 取得全部 `REQ/AC/UDES`，不得从任务表、索引或快照 JSON 反推目标集合。若当前文档与最后确认记录不一致，先裁决哪些修订已获用户确认。
2. 范围较大时可用 `workctl index` 重建当前索引，再使用 `taskctl completion-context`。工具必须从当前 Markdown 返回目标，即使快照或缓存漂移也只附加诊断。如果分页，保存首页 `snapshot_id` 并随单一结果流游标传回；任务或文档在复核中变化时，为防止混用证据快照，从第一页重审。
3. 检查 `CON` 约束以及全部当前 `DCR` 的原始状态与内容；CLI 不得根据内置状态集隐藏条目。只要某项表明受保护目标尚未满足，就不能声明最终完成。
4. 本次方案改变长期 owner 或契约时，复核修改前后影响集合中的适用消费者与派生产物，确认各项已经证明仍有效或完成更新、迁移、退出、重做或重新验证，并排除来源版本未知或陈旧的结果。
5. 只有全部需求和全部用户设计均成立、整体结果没有以局部正确偏离确认目标，且所选实现的必要影响闭环已经形成时才报告当前范围完成。模型设计审核、现状审核、方案审核、任务完成率和 CLI 检查只能分别报告为中间阶段结果。

## 与专项 skill 协同

- 根因或职责入口判断由 `$change-governance` 提供方法，结论分别进入 `OBS/DES/SOL`。
- 代码结构、C++、空间、UE 等判断由对应 skill 产生证据或实现结果，交付链只保存引用和简要结论。
- `$task-table-manager` 返回的任务上下文应包含精确上游条目和前置结果，不要求执行者读取全部阶段文档。
- `$reasoning-governor` 只调节 active Goal 的 next-turn 深度，不写入任务状态或阶段文档。
