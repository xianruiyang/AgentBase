# 受保护目标合同

本文件唯一维护需求、用户设计、确认快照和延后讨论项的阶段语义；通用 ID 与条目格式继承 [artifact-contracts.md](artifact-contracts.md)。

## 需求分析

- `REQ` 说明用户要获得的结果、适用对象和范围。
- `AC` 说明可直接判断的完成条件、验证主体和边界。
- `CON` 说明约束、非目标、授权边界和外部限制。

初始表达只是共同理解问题的输入，不假定其中的术语、事实判断、原因解释或实现建议准确完整。先从实际场景和用户期望改变的可观察结果重组候选意图，再结合项目目标、直接证据、历史决策、受影响对象和长期后果识别会改变结果的隐含需求、冲突与取舍；向用户说明重组依据、不确定性和实质差异后共同校准。

期望结果进入 `REQ`，待核实的现状或原因保持为证据问题；用户明确把实现办法指定为设计约束时进入 `UDES`。若该办法只是用于表达期望结果或猜测原因与方案，则先作为模型设计的候选输入，说明实质影响和替代后再确认是否成为 `UDES`。不得把不准确术语、当前实现、模型偏好或为适配现状而缩小的目标写成需求；所有会改变目标或验收的选择由用户裁决。

## 用户设计

- `UDES` 只记录用户明确指定为设计约束，或在候选意图、影响与替代方案澄清后确认的职责、接口、结构、流程、呈现、优先级或技术选择。
- 模型为实现目标推导的技术选择进入 `DES`，不得伪装成用户设计。
- 用户确认后与需求一起构成当前执行周期的受保护目标；执行闭环中不得静默编辑。

## 确认来源与目标保护

在文档中保留用户确认来源。需要跨轮核对时，可用 `workctl protect` 记录 `confirmed_by=user`、非空 `confirmation_ref`、`cycle_id`、文档指纹和当时 ID。模型提供的 `confirmation_ref` 使用短语义来源（如 `current-user-request`），不复制对话 UUID、哈希或其他机器身份；完整字段只进入 machine 资产，不在 model 回执重复。`protected-baseline.json` 只是确认来源的快照元数据；哈希、ID 数量和确认字段不能反向证明目标内容正确或用户已经确认。

快照与当前 Markdown 不一致时，模型回到用户确认记录裁决当前周期目标。新执行周期可保留旧快照历史；CLI 不签发执行许可，也不因缺少快照替代文档判断。

## 延后讨论项

执行证据表明必须改变 `REQ/AC/CON/UDES` 才能继续时建立 `DCR`，至少写明目标 ID、直接证据、为何不能由模型设计或方案调整解决、受影响工作、仍可继续的工作和建议讨论内容。原受保护条目保持不变。

`DCR` 可使用 `deferred`、`discussed`、`resolved` 或 `withdrawn` 状态。除非用户主动要求立即讨论，先完成不依赖该变更的工作，再集中提交用户；只有重新商议并由用户明确确认，才能在后续执行周期修订受保护目标。模型不得自行接受 DCR。

索引和最终复核上下文必须保留当前 Markdown 中全部 `DCR` 及其原始状态，不得用内置状态集筛除非标准、缺失或其他状态。状态偏差只形成诊断；条目是否仍表明目标无法满足，由模型依据本文、用户确认和当前证据裁决。
