## 工作区

```text
<work-dir>/
├── workflow.json
├── protected-baseline.json
├── requirements.md
├── user-design.md
├── design.md
├── current-state.md
├── solution.md
├── deferred-changes.md
├── task-table.json
├── tasks/
├── state/
├── results/
├── TASK_TABLE.md
└── .work-cache/index.json
```

`requirements.md` 和 `user-design.md` 持有执行前由用户确认的受保护语义；`design.md`、`current-state.md` 和 `solution.md` 持有模型可持续修订的语义。任务与结果只引用这些文档中的稳定 ID。生成视图和缓存不定义目标或完成状态。

`protected-baseline.json` 必须记录 `confirmed_by=user` 和非空 `confirmation_ref`；前者限定确认主体，后者定位本轮用户确认依据。工具在创建和每次读取时同时验证来源、文档哈希与精确 ID，任何一项都不能替代其他项。

## 稳定 ID

| 前缀 | 所属产物 | 含义 |
| --- | --- | --- |
| `REQ-` | requirements | 用户可观察结果 |
| `AC-` | requirements | 原子验收条件 |
| `CON-` | requirements | 约束或明确非目标 |
| `UDES-` | user-design | 用户明确给出的设计 |
| `DEC-` | 可修订阶段 | 仍需裁决或已经裁决的模型选择 |
| `DES-` | design | 模型形成的目标职责、接口、状态或依赖 |
| `OBS-` | current-state | 有证据边界的当前观察 |
| `GAP-` | current-state | 目标相对现状的差距 |
| `SOL-` | solution | 解决差距的具体动作与结果 |
| `DCR-` | deferred-changes | 对受保护基线的延后讨论项 |
| `T` | tasks | 可执行工作包 |

ID 创建后保持稳定。内容变化修改正文和状态；只有对象本身被证明不是同一个对象时才新建 ID。引用写出精确 ID，不使用名称相似或隐含顺序代替关系。

索引只从项目符号形式的明确关系字段提取引用：`关联`、`关联需求`、`关联目标`、`满足`、`解决`、`依赖`、`后继证据` 和 `目标ID`（以及其直接英文对应词）。标题、来源、证据描述、正文与代码示例中的 ID 形文本只是文字，不进入语义图；需要关系时必须写入上述字段。

## 通用条目格式

每个语义条目使用二级标题：

```markdown
## REQ-001 用户可以导出当前结果

- 状态: confirmed
- 来源: 用户请求
- 关联: AC-001, CON-002

正文只写本条职责内的内容。
```

可修订条目推荐使用 `confirmed`、`proposed`、`open`、`unknown` 或 `superseded`。`open` 与 `unknown` 必须保持可见，但不会因为工具检查而自动阻断其他条目。受保护条目只使用 `confirmed`；需要改变时不得把原条目标为 `superseded`，而应建立 `DCR`。

## 各阶段内容

### 需求分析

- `REQ`：用户结果、适用对象和范围。
- `AC`：可直接判断的完成条件、验证主体和边界。
- `CON`：约束、非目标、授权边界和外部限制。
- 执行前所有会改变目标或验收的选择都必须与用户商议完成，不能把未决 `DEC` 带入受保护需求。

不得写实现模块、当前代码推断或为了适配现状而缩小的目标。用户确认后运行 `workctl protect`；执行闭环中不得编辑本文件。

### 用户设计

- `UDES`：用户明确要求的职责、接口、结构、流程或技术选择。
- 只记录用户实际给出的设计，不把模型推导伪装成用户设计。
- 用户确认后与需求一起固化；执行闭环中不得编辑。

### 模型设计

- `DES`：模型为满足 `REQ/AC/UDES` 形成的职责、接口、状态、依赖和生命周期。
- 明确引用所满足的 `REQ/AC` 与适用 `UDES`。
- 不描述当前代码是否已经做到，也不把候选方案写成目标职责。
- 执行中可根据新证据修订；修订后检查对现状、方案和任务的影响。

### 现状分析

- `OBS`：来源、对象、环境、观察结果及证据能证明的上限；标记直接事实、推断或未知。
- `GAP`：引用目标 `DES/AC` 和相关 `OBS`，只说明哪里尚未满足。
- 根因尚未证明时写为假设或未知，不混入解决动作。

### 方案设计

- `SOL`：引用所处理的 `GAP` 与 `DES`，写出动作、预期结果、依赖、影响范围、风险和验证方式。
- 真实候选存在差异时记录选择依据；关键选择未决时保留 `DEC`。
- 不把“以后确认”“由 owner 处理”或含糊等价能力当作可执行动作。

### 任务与结果

- 任务只承载可执行动作，引用 `SOL/GAP/DES/AC/REQ`，并声明依赖、产出、修改范围和验证方式。
- 结果只记录实际产出、有效验证、改变的文件、未解决问题和被推翻的上游 ID。
- 状态、表格行数或结果文件存在都不证明上游语义或产品行为正确。

### 延后讨论项

当执行证据表明必须改变 `REQ/AC/CON/UDES` 才能继续时，建立 `DCR`，至少写明目标 ID、直接证据、为何不能由模型设计或方案调整解决、受影响工作、仍可继续的工作和建议讨论内容。原受保护条目保持不变。

`DCR` 使用 `deferred`、`discussed`、`resolved` 或 `withdrawn` 状态。除非用户主动要求立即讨论，`deferred` 项在其余不依赖该变更的内容完成后集中提交用户。只有用户重新商议并明确确认，才能在后续执行闭环建立新的受保护基线；模型不得自行接受 DCR。任何仍表明 `REQ/AC/UDES` 无法满足的延后项都会使当前范围不能最终完成。

## 最终完成合同

当前范围的最终目标集合只由受保护基线中的全部 `REQ/AC/UDES` 构成；建立基线时至少存在其中一项，不能只有约束而没有目标。最终复核必须逐项找到直接适用的执行结果和验证证据，并确认 `CON` 约束仍满足。

`DES/OBS/GAP/SOL/DEC`、任务合同、任务状态、生成视图、引用覆盖和工具诊断都是中间阶段产物。它们可以通过各自审核，但任何一个或全部通过都不能替代用户基线完成；任务 `done` 也只能表示该任务记录的结果已提交。
