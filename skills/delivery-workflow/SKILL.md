# Delivery Workflow

阶段文档是交付规则与语义真源，模型依据用户确认和证据裁决。`workctl` 只辅助模板、来源快照、索引、引用查询和有界上下文；工具状态、结构、链接和诊断不代替语义判断。

## 职责协同

- 运行前沿与扩量/重裁归 `$execution-governor`；本 skill 只回写结论。
- 本 skill 维护 `需求 → 目标设计 → 现状分析 → 方案设计 → 任务设计 → 执行反馈`；需要持久任务、依赖图、多人状态或跨轮恢复时同时使用 `$task-table-manager`。后者只持有任务合同、状态和结果摘要，任务以稳定 ID 引用上游，不复制或裁决上游语义。
- 根因、职责、权威入口、共享职责形成、权威变化的跨消费者影响或共享阻断检查确实需要专项裁决时再使用 `$change-governance`，并把结论写回其所属的现状、设计或方案条目，不建立平行计划。
- 最终复核仅在用户明确要求完整审计，或跨目标、入口、迁移阶段或验证合同而普通判断不足时使用 `$change-governance`；稳定上游的需求、用户设计、约束与执行证据由本 skill 核对。
- 实施阶段继续按任务本身触发 C++、符号、搜索、PowerShell、空间等领域 skill；本 skill 不复制它们的规则。
- 推理深度只在用户明确要求时由 `$reasoning-governor` 读写，不由交付阶段、任务难度或执行状态触发。

## 工作区与工具

- 默认把长期交付链放在 `docs/work/<YYYYMMDD>_<NAME>/`；项目已有正式位置时沿用项目约定。
- 创建或修改交付产物（阶段 Markdown、任务/结果合同或结构），或执行最终复核时先读 [artifact-contracts.md](references/artifact-contracts.md)；其余只读消费不加载。
- 再按职责读：[target-contracts.md](references/target-contracts.md) 用于创建或修改需求/用户设计、目标保护与漂移、DCR 或最终复核；[planning-contracts.md](references/planning-contracts.md) 管设计、现状与方案；[execution-contracts.md](references/execution-contracts.md) 管任务、结果、状态、证据回流与完成。同次修改方案及任务、结果、状态或证据时双读 planning/execution；只投影已确认方案为任务时读 execution；未涉及上述 target 职责时不读 target。
- 判断阶段推进、回退、新证据影响、执行上下文、证据回流或最终复核时读取 [iteration.md](references/iteration.md)；最终复核同时读取公共产物、目标与执行合同。实际使用 `workctl` 时读取 [tooling.md](references/tooling.md)。完整链在进入相应动作时逐步加载，不预读尚未需要的细则。
- 工具入口是 PATH 中的 `workctl`，显式传绝对 `--work-dir`；不可用时不从 skill 找脚本。默认 `--view model` 返回当前动作的稀疏证据，写入回执只留状态、来源、输出与实际问题，列表仅截断时附总数。程序、测试或完整结构检查才用 `--view machine`，模型预算不足不得以其恢复。两种视图来自同一文档索引；CLI 缺失或诊断不改变文档确定的目标或授权。
- `requirements.md` 保存与用户商议确认的需求，`user-design.md` 保存用户明确给出的设计，`design.md` 只保存模型形成的设计。需要跨轮保留确认来源时，可用 `workctl protect` 记录内容指纹与条目清单。
- Markdown 阶段文档是模型与用户直接读取、按稳定 ID 局部维护的语义真源；修改所属条目并删除失效重复，不写逐轮日志、派生计数或跨阶段同步摘要。`workflow.json` 只登记文件与索引位置，`protected-baseline.json` 只存确认来源快照元数据，`.work-cache/index.json` 和生成视图可重建；模型不得编辑它们改变阶段语义。快照与文档不一致时只诊断，由模型按用户确认记录裁决当前周期目标。

## 执行原则

1. 按目标合同接纳明确且无冲突的要求，保留用户确认来源；只有会改变动作的歧义、冲突、错误前提或实现设想与结果不一致时才校准，不因进入交付阶段重新解释或重复确认已有合同。
2. 设计持有所需职责、接口、状态、生命周期及消费者差异；实现事实与目标差距留在现状分析，不把现状写成设计约束。
3. 现状核查实际消费者、派生物及绕过/复制路径，未查部分保持未知。
4. 方案处理已确认差距，包含 owner 修正、消费者接入、旧同责路径退出及验证；未决选择不伪装成可执行任务。
5. 只把可以执行且有真实产出的方案动作投影为任务。任务引用上游 ID，用依赖和消费关系表达公共产出与接入，不复制整段文档；共享前提的证明和首个消费者按真实消费形成依赖。
6. 执行前先形成当前动作的最小语义闭包；现有证据不足以可靠决定动作时，按迭代合同继续扩展，而不是默认重读全部阶段、历史或相邻分支。
7. 命中 `$execution-governor` 时按其前沿、维度和消费者路径行动；消费者证据立即回流。反例改变范围或下一动作时，先更新所属阶段与任务状态再继续；任务深度、数量或完成率不替代前沿。
8. 执行中可以持续修订模型设计、现状分析、方案和任务。若证据显示必须改变需求或用户设计，不改原条目；写入 `deferred-changes.md`，完成所有不依赖该变更的工作后再与用户讨论。
9. 持续检查设计、方案、任务和结果在语义、范围、优先级与可观察结果上对齐目标。偏离或新证据推翻可变上游时，先保留原影响集并修订最早失效条目，再按任务依赖和实际系统复核、写回新旧影响，必要时用 `impact` 定位；技术便利、状态计数或未登记关系不得掩盖目标变化。
10. 报告进度时分别说明任务状态、可修订上游未决项、延后讨论项和已有验证结果；工具输出只是这些判断的低成本输入。
11. 只按当前周期共同澄清并由用户确认的文档目标判断完成：全部 `REQ/AC/UDES` 有直接适用证据，整体结果未以局部正确偏离目标，也无表明目标未满足的延后讨论项；改变长期 owner 或契约还须闭合适用消费者与证据。设计、分析、方案、任务状态、快照、索引、结构检查和阶段审核都只是中间结果。

## 轻量使用

- 单一阶段请求只编写该阶段及其必要输入，不为形式完整创建整个工作区。
- 已有完整规格的单轮实现不触发本 skill。
- 阶段文件较少时直接编辑和读取；只有重复查询、跨轮恢复或范围较大时才运行 `workctl`。CLI 不可用时仍按同一文档合同继续。
