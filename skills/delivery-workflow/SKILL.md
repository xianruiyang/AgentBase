# Delivery Workflow

阶段文档定义交付规则与语义真源，模型基于用户确认和证据裁决。`workctl` 只辅助创建模板、快照来源、建立索引、查询引用和生成有界上下文；工具可用与否、结构完整度、链接数量和诊断都不能代替对需求、设计、现状、方案和结果的专业判断。

## 职责协同

- 运行前沿与扩量/重裁归 `$execution-governor`；本 skill 只回写结论。
- 本 skill 维护 `需求 → 目标设计 → 现状分析 → 方案设计 → 任务设计 → 执行反馈` 的语义链；需要持久任务、依赖图、多人状态或跨轮恢复时同时使用 `$task-table-manager`。
- `$task-table-manager` 只持有任务合同、执行状态和结果摘要，不复制或裁决上游语义。任务通过稳定 ID 引用本 skill 的产物。
- 根因、职责、权威入口、共享职责形成、权威变化的跨消费者影响或共享阻断检查确实需要专项裁决时再使用 `$change-governance`，并把结论写回其所属的现状、设计或方案条目，不建立平行计划。
- 最终复核跨越受保护需求、用户设计、约束与执行证据时，使用 `$change-governance` 的完成审计方法；它只加强证据复核，不替代本 skill 定义的最终目标集合。
- 实施阶段继续按任务本身触发 C++、符号、搜索、PowerShell、空间等领域 skill；本 skill 不复制它们的规则。
- 命中 `$execution-governor` 时由其裁决目标档位，否则按全局判断；`$reasoning-governor` 只管理线程设置。

## 工作区与工具

- 默认把长期交付链放在 `docs/work/<YYYYMMDD>_<NAME>/`；项目已有正式位置时沿用项目约定。
- 阶段产物先读公共 [artifact-contracts.md](references/artifact-contracts.md)，再按实际修改类型读：[target-contracts.md](references/target-contracts.md) 管需求、用户设计、目标保护与 DCR，[planning-contracts.md](references/planning-contracts.md) 管设计、现状与方案，[execution-contracts.md](references/execution-contracts.md) 管任务、结果、状态、证据回流与完成。仅同次修改方案语义与任务/结果合同才双读 planning/execution；消费已确认方案投影任务只读 execution。只遵守已确认目标且无漂移、DCR 或最终复核时不因此额外读取目标合同。
- 判断阶段推进、回退、新证据影响、执行上下文、证据回流或最终复核时读取 [iteration.md](references/iteration.md)；最终复核同时读取公共产物、目标与执行合同。实际使用 `workctl` 时读取 [tooling.md](references/tooling.md)。完整链在进入相应动作时逐步加载，不预读尚未需要的细则。
- 工具入口是 `<SkillDir>/scripts/workctl.py`。只在它能降低编辑或查询成本时使用，并显式传绝对 `--work-dir`；默认 `--view model` 返回当前阶段动作的稀疏证据，protect/render 等写入回执只保留当前状态、来源、输出位置与实际问题，影响列表只在截断时额外返回总数。程序、测试或完整结构检查显式使用 `--view machine`。两种视图来自同一次文档索引事实计算；不得因 CLI 缺失或诊断而改变文档已确定的目标或实施授权。
- `requirements.md` 保存与用户商议确认的需求，`user-design.md` 保存用户明确给出的设计，`design.md` 只保存模型形成的设计。需要跨轮保留确认来源时，可用 `workctl protect` 记录内容指纹与条目清单。
- `workflow.json` 只登记工作区文件与索引位置；Markdown 阶段文档是语义真源，`protected-baseline.json` 只是用户确认来源的快照元数据，`.work-cache/index.json` 和生成视图可随时重建。快照与当前文档不一致时报告诊断，由模型根据用户确认记录裁决当前执行周期的目标。
- 阶段 Markdown 是模型与用户直接读取、由模型按稳定 ID 局部维护的正式交互面；修改时更新条目所属职责并删除失效重复，不把逐轮日志、派生计数或同一事实的同步摘要写入其他阶段。`workflow.json`、保护快照、缓存和生成视图只承担各自结构化职责，模型不通过编辑生成物改变阶段语义。

## 执行原则

1. 把初始表达当作线索而非完整规格；从实际场景、用户要改变的可观察结果、项目证据、历史决策与长期后果重组候选意图，区分结果、事实陈述、原因猜测与实现建议，说明依据和不确定性后共同确认需求及用户设计并保留来源；用户最终裁决，不得静默替用户改写目标。
2. 写模型设计时确定满足当前用户确认目标所需的权威职责、接口、状态、生命周期、当前消费者和依赖方向；共同决定与消费者差异分开表达，当前实现事实留到现状分析。
3. 现状分析分开记录直接观察、推断和未知，并检查实际 owner、消费者、派生产物、绕过或复制路径，再按当前用户确认目标及模型设计形成差距。
4. 方案设计只处理已确认差距，写清动作、结果、依赖、风险和验证方式；涉及共享职责时把 owner 修正、当前消费者接入、旧同责路径退出和验证形成闭环，选择仍未决时保留候选，不伪装成任务。
5. 只把可以执行且有真实产出的方案动作投影为任务。任务引用上游 ID，用依赖和消费关系表达公共产出与接入，不复制整段文档；共享前提的证明和首个消费者按真实消费形成依赖。
6. 执行前先形成当前动作的最小语义闭包；现有证据不足以可靠决定动作时，按迭代合同继续扩展，而不是默认重读全部阶段、历史或相邻分支。
7. 命中 `$execution-governor` 时按其前沿、维度和消费者路径行动；消费者证据立即回流。反例改变范围或下一动作时，先更新所属阶段与任务状态再继续；任务深度、数量或完成率不替代前沿。
8. 执行中可以持续修订模型设计、现状分析、方案和任务。若证据显示必须改变需求或用户设计，不改原条目；写入 `deferred-changes.md`，完成所有不依赖该变更的工作后再与用户讨论。
9. 执行中检查设计、方案、任务和结果仍在语义、范围、优先级与可观察结果上对齐目标；偏离或新证据推翻可变上游时，先保留原影响集并修订最早失效条目，再结合 `impact`、任务依赖和实际系统复核新旧影响并写回；不让技术便利、状态计数或未登记关系掩盖目标变化。
10. 报告进度时分别说明任务状态、可修订上游未决项、延后讨论项和已有验证结果；工具输出只是这些判断的低成本输入。
11. 最终完成只按当前执行周期内共同澄清并由用户确认的文档目标判断：全部 `REQ/AC/UDES` 都有直接适用的完成证据，整体结果未以局部正确偏离目标，且不存在表明其未满足的延后讨论项；改变长期 owner 或契约时还须闭合适用消费者与证据。模型设计、分析、方案、任务状态、快照、索引、结构检查和各阶段审核都只是中间结果。

## 轻量使用

- 单一阶段请求只编写该阶段及其必要输入，不为形式完整创建整个工作区。
- 已有完整规格的单轮实现不触发本 skill。
- 阶段文件较少时直接编辑和读取；只有重复查询、跨轮恢复或范围较大时才运行 `workctl`。CLI 不可用时仍按同一文档合同继续。
