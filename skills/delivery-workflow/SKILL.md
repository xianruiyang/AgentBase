# Delivery Workflow

阶段文档定义交付规则与语义真源，模型基于用户确认和证据裁决。`workctl` 只辅助创建模板、快照来源、建立索引、查询引用和生成有界上下文；工具可用与否、结构完整度、链接数量和诊断都不能代替对需求、设计、现状、方案和结果的专业判断。

## 职责协同

- 本 skill 维护 `需求 → 目标设计 → 现状分析 → 方案设计 → 任务设计 → 执行反馈` 的语义链；需要持久任务、依赖图、多人状态或跨轮恢复时同时使用 `$task-table-manager`。
- `$task-table-manager` 只持有任务合同、执行状态和结果摘要，不复制或裁决上游语义。任务通过稳定 ID 引用本 skill 的产物。
- 根因、职责、权威入口、共享职责形成、权威变化的跨消费者影响或共享阻断检查确实需要专项裁决时再使用 `$change-governance`，并把结论写回其所属的现状、设计或方案条目，不建立平行计划。
- 最终复核跨越受保护需求、用户设计、约束与执行证据时，使用 `$change-governance` 的完成审计方法；它只加强证据复核，不替代本 skill 定义的最终目标集合。
- 实施阶段继续按任务本身触发 C++、符号、搜索、PowerShell、空间等领域 skill；本 skill 不复制它们的规则。
- 推理深度、对话历史和项目 metadata 继续由各自正式 skill 管理，不进入交付链状态。

## 工作区与工具

- 默认把长期交付链放在 `docs/work/<YYYYMMDD>_<NAME>/`；项目已有正式位置时沿用项目约定。
- 先完整读取 [artifact-contracts.md](references/artifact-contracts.md) 建立或修改阶段产物；需要判断阶段推进、回退或新证据影响时读取 [iteration.md](references/iteration.md)；使用 CLI 时读取 [tooling.md](references/tooling.md)。
- 工具入口是 `<SkillDir>/scripts/workctl.py`。只在它能降低编辑或查询成本时使用，并显式传绝对 `--work-dir`；不得因 CLI 缺失或诊断而改变文档已确定的目标或实施授权。
- `requirements.md` 保存与用户商议确认的需求，`user-design.md` 保存用户明确给出的设计，`design.md` 只保存模型形成的设计。需要跨轮保留确认来源时，可用 `workctl protect` 记录内容指纹与条目清单。
- `workflow.json` 只登记工作区文件与索引位置；Markdown 阶段文档是语义真源，`protected-baseline.json` 只是用户确认来源的快照元数据，`.work-cache/index.json` 和生成视图可随时重建。快照与当前文档不一致时报告诊断，由模型根据用户确认记录裁决当前执行周期的目标。

## 执行原则

1. 把初始请求作为共同理解问题的起点；结合项目目标、直接证据、历史决策、受影响对象和长期后果识别会改变结果的隐含需求、冲突与取舍，向用户说明后共同确认需求及用户设计，并保留确认来源；用户保有最终裁决权，不得从现有实现、模型偏好或任务困难反向改写目标。
2. 写模型设计时确定满足当前用户确认目标所需的权威职责、接口、状态、生命周期、当前消费者和依赖方向；共同决定与消费者差异分开表达，当前实现事实留到现状分析。
3. 现状分析分开记录直接观察、推断和未知，并检查实际 owner、消费者、派生产物、绕过或复制路径，再按当前用户确认目标及模型设计形成差距。
4. 方案设计只处理已确认差距，写清动作、结果、依赖、风险和验证方式；涉及共享职责时把 owner 修正、当前消费者接入、旧同责路径退出和验证形成闭环，选择仍未决时保留候选，不伪装成任务。
5. 只把可以执行且有真实产出的方案动作投影为任务。任务引用上游 ID，用依赖和消费关系表达公共产出与接入，不复制整段文档。
6. 有效规划后控制无必要的横向展开；在用户优先级、硬依赖、关键风险、共享前置和质量允许时，优先沿当前目标链形成最近的可验证交付闭环，并立即用证据确认或修正方案、模型设计和需求达成判断。任务深度只作闭环距离线索，不覆盖必要取证、用户裁决、影响闭合或验证。
7. 执行中可以持续修订模型设计、现状分析、方案和任务。若证据显示必须改变需求或用户设计，不改原条目；写入 `deferred-changes.md`，完成所有不依赖该变更的工作后再与用户讨论。
8. 执行中持续检查设计、方案、任务和结果在语义、范围、优先级与用户可观察结果上仍对齐确认目标；发现偏离或新证据推翻可变上游判断时，先保留修改前影响集合，回到最早失效条目修订，再结合 `impact`、任务依赖和实际系统复核旧、新影响并写回裁决；不让技术便利、状态计数或未登记关系掩盖目标变化。
9. 报告进度时分别说明任务状态、可修订上游未决项、延后讨论项和已有验证结果；工具输出只是这些判断的低成本输入。
10. 最终完成只按当前执行周期内共同澄清并由用户确认的文档目标判断：全部 `REQ/AC/UDES` 都有直接适用的完成证据，整体结果未以局部正确偏离目标，且不存在表明其未满足的延后讨论项；改变长期 owner 或契约时还须闭合适用消费者与证据。模型设计、分析、方案、任务状态、快照、索引、结构检查和各阶段审核都只是中间结果。

## 轻量使用

- 单一阶段请求只编写该阶段及其必要输入，不为形式完整创建整个工作区。
- 已有完整规格的单轮实现不触发本 skill。
- 阶段文件较少时直接编辑和读取；只有重复查询、跨轮恢复或范围较大时才运行 `workctl`。CLI 不可用时仍按同一文档合同继续。
