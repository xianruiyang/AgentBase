- 状态: confirmed
- 来源: `global/AGENTS.md` 修改前正文

## OBS-014 `complete` 两阶段写入允许结构有效的下一 revision 结果静默存在

- 状态: confirmed
- 来源: `taskctl.py` 修改前 `command_complete`、`result_history_diagnostics` 与 partial-write recovery
- 证据上限: 只覆盖 result 已落盘、state 尚未提交的结构边界，不证明结果正文或验证语义有效

`complete` 先写 `results/<ID>.r<state+1>.json` 再原子写 state；相同内容重试本来能够恢复。但读取诊断允许 `state+1` 的结构有效结果且不报告其尚未被 state 引用，导致最需要恢复的中间态没有可见信号。自动推进 state 会越过模型完成判断，硬阻断读取又会破坏已有恢复路径。

## OBS-015 昂贵动作已有停止原则但缺少最小充分 preflight 合同

## OBS-017 当前实现尚未收敛时启动了长回归

- 证据上限: 证明已知 owner 的简单修改可以不选治理 skill，但不证明模型会按当前动作而非项目总体规模稳定选择该路径

现有合同分别排除了机械任务、稳定上游普通实现和无共享前提的执行控制，却没有用同一组可观察条件说明何时直接读改验收并停止。大型项目背景仍可能让模型对一个已知 owner 的局部动作重新加载完整交付链或治理审计；继续新增专项排除用例不会形成统一停止边界。

## GAP-016 局部任务缺少按当前动作判定的统一执行与停止条件

- 状态: confirmed
- 关联: AC-073, OBS-018

需要把 owner、契约、验收、共享未知和长期职责变化合成一条全局快速路径，并让既有局部边界用例验证该行为；一旦这些条件失效仍返回对应深层 owner，而不是把快速路径绝对化。

## OBS-019 子代理合同把实验生命周期边界与只读边界混在一起

- 状态: confirmed
- 来源: 修改前 `global/agents/evidence.toml`、`global/agents/experiment.toml` 与 `skills/subagent-orchestration`；用户对真实连续实现试错和交接 Token 的补充
- 证据上限: 证明当前文本容易把“实验代码不是生产实现”理解为“实验不能改代码”，且交付模板包含可重复字段；不证明每次子代理实际输出都冗长或只读

`evidence` 与 `experiment` 已有稳定身份、隔离范围和主代理接纳责任，但两个交付模板仍接近完整报告；`experiment` 同时写“只写隔离范围”“不得修改生产真源”“补丁不直接合入”，没有明确可在可回滚隔离面真实改代码，也没有覆盖前一失败连续遮蔽后续问题、主代理因而反复小改并启动昂贵验证的试路场景。

## GAP-017 子代理缺少稀疏决策交付与连续遮蔽问题的可回滚实验语义

- 状态: confirmed

需要把所有子代理交接收敛为只含非空、可逐项接纳且能改变主代理裁决的最小证据包；同时允许 `experiment` 在有恢复依据且不污染无关 dirty 内容的隔离面迭代修改实验代码，以有界探针提前发现可行路径和有证据支持的后继约束。实验补丁仍须由主代理按正式 owner 与契约重写、修订接入或拒绝，不能自动转正。

## OBS-020 现有维度规则没有把测试编写本身纳入横向扩量

- 状态: confirmed
- 来源: 修改前 `global/AGENTS.md`、`execution-governor`、Delivery Workflow 与 Task Table Manager 合同
- 证据上限: 证明规则已要求最小判别组合、首个真实消费者与不机械展开笛卡尔积，但没有明确批量实现、fixture、示例和测试代码在运行前已经形成横向投入

现有规则主要在“选择验证组合”和“执行昂贵批量验证”处约束扩量。模型仍可把为所有平级组合预先编写测试解释成纵向路径的准备工作；即使测试尚未运行，已产生的 fixture、oracle、代码和维护责任也会锁定未验证判断并延迟首个可用结果。

## OBS-021 真实多组件任务因逐组合编写测试而停滞

- 状态: confirmed
- 来源: 用户对当前真实工作流的直接观察与后续目标校准
- 证据上限: 证明 AgentBase 支持范围内出现了组合数量爆炸、逐组合测试编写和纵向闭环迟滞；缺少该次路由/引用 trace，不能单独区分 `route_or_reference_missing` 与 `action_noncompliant`

用户进一步明确，上游内容应先完成设计，执行阶段不是用第一条路径演化架构，而应在既定设计与职责内深度优先完成一个可用结果，尽早验证需求和设计、快速纠偏；其他平级实现和最终测试矩阵随后仍按原设计完成。

## GAP-018 最小纵向路径没有约束实现与测试的横向准备

## GAP-019 等价依据没有形成可执行的组合覆盖证明

- 状态: confirmed
- 关联: AC-075, OBS-020, OBS-021

当前合同要求识别维度与等价依据，却没有规定如何由组件契约、接口接缝、真实交互、代表 case 和历史回归组成覆盖，也没有说明 pairwise、参数化与穷举的证据边界。为避免越界声明，模型可能退化为逐 tuple 直接取证；反向简单规定 pairwise 又会漏掉真实高阶耦合。

## OBS-022 第四版规则存在但真实 UE 执行仍横向展开

- 状态: confirmed
- 来源: 2026-09-03 用户提供的 UeAgentInterface15 自查与最近子代理原始事件复核
- 证据上限: 证明支持场景中出现公共消费者合同未稳即展开多个领域、生产缺口与旧测试迁移交织、PCG/Deformer 绑定批量验证和失败逐层暴露；不单独裁决该 UE 项目的正确合同或具体修复

现有规则已要求首个正式消费者闭环，但没有在修改动作入口要求显式锁定公共合同、唯一活动消费者、有效 oracle 与暂缓范围。模型因此可以在文字上认可纵向原则，同时在生产代码、fixture、测试和构建批次上继续切换消费者，并用代码量或并行分支替代闭环进展。

## OBS-023 并行子代理结果超过主线即时接纳能力

- 状态: confirmed
- 来源: 同一真实任务的子代理创建与交付记录
- 证据上限: 证明多个子代理分别取得大量有效问题，但主线在前提尚未闭合时同时接收多个分支；不证明固定减少子代理数量总能改善结果

问题不是 evidence 输出普遍无效，而是返回项可能共同依赖或推翻同一上游；主代理尚未接纳首个决定性反例时，其他分支继续取证和主线继续实现会共同扩大返工范围。

## GAP-021 首错后的 preflight 与子代理接纳仍可横向扩散
