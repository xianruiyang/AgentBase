# Task completion 写入合同需求

## REQ-001 模型只编写完成结果的语义正文

- 状态: confirmed
- 来源: 用户要求模型直接阅读和修改的内容采用最小充分设计，而程序输出保持稳定完整
- 关联: AC-001, AC-002, AC-003, AC-004, AC-005

`taskctl complete` 应让模型只维护实际结果、产出、修改、验证、未决和证据等语义内容；任务身份、合同 revision、永久 schema 和来源快照持久化由工具在写入边界负责。永久结果仍须保留程序读取所需的稳定完整机器合同。

## AC-001 任务身份和执行版本不由模型结果正文重复维护

- 状态: confirmed
- 来源: REQ-001
- 关联: REQ-001

模型结果输入不要求 `schema`、`task_id` 或 `task_revision`。任务身份来自命令目标，实际执行依据的任务 revision 通过显式 CAS 参数传入并与当前合同比较，工具不得用完成时当前值静默替代执行依据。

## AC-002 永久结果只有一种完整机器表示

- 状态: confirmed
- 来源: REQ-001
- 关联: REQ-001

工具把语义输入规范化为现有 `task.result` 永久格式，并注入任务身份、执行 revision 和来源快照引用。查询、历史读取和 machine 视图继续消费同一种永久结果，不建立第二状态源。

## AC-003 新写入不得产生失效的来源快照引用

- 状态: confirmed
- 来源: REQ-001 与项目机械门禁合同
- 关联: REQ-001

完成输入显式携带来源快照引用时，工具必须在结果或状态发生变化前确认资产存在、结构可读且内容身份与引用一致；无法解析的引用阻断本次写入并返回恢复动作。来源覆盖不完整、相对当前索引陈旧或完全未提供收据仍只作为语义诊断。

## AC-004 历史异常和真实旧输入保持单向兼容

- 状态: confirmed
- 来源: 已确认的 Task 来源快照收据 AC-004
- 关联: REQ-001

已经落盘的历史结果即使资产后来缺失或损坏，仍通过查询诊断保持可见，不改写历史。上一版完整 `task.result` 完成输入继续由唯一 `complete` 入口规范化；所有新永久写入仍只产生当前机器格式和单一来源表示。

## AC-005 写入失败不改变任务状态或结果历史

- 状态: confirmed
- 来源: REQ-001 与项目原子写入、CAS 约束
- 关联: REQ-001

任务 revision 冲突、状态 revision 冲突、来源快照引用不可解析或已有同名结果冲突时，本次 completion 不得推进状态、创建新的结果历史或覆盖已有记录；修复输入后可以从明确恢复动作重试。

## CON-001 本轮边界

- 状态: confirmed
- 来源: 用户要求持续开发；项目发布合同要求每次 Codex 发布另行明确同意
- 关联: REQ-001

本轮可以修改仓库真源、正式合同和本地验证资产，但不执行 Codex `Publish`，不混入插件迁移或猜测式快照回收。
