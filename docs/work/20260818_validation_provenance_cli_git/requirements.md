# 验证溯源、CLI 帮助与 Git 基线：需求

## REQ-001 正式验证不能靠原样重跑刷到成功

- 状态: confirmed
- 来源: 用户要求“做 1”及紧邻讨论
- 关联: AC-001, AC-002

路由评估的每次正式接收都应留下可审计、文本有界的结果收据；相同候选与输入的新运行必须显式说明有限重试理由，不能用重复运行替代原因修正或输入变化。

## AC-001 失败与变化可追溯

- 状态: confirmed
- 来源: REQ-001

收据能够定位 phase、候选、评估输入、capsule、结果、evaluator、UTC 时间、通过或失败、失败分类及相对前次发生变化的身份字段；不复制原始大日志。

## AC-002 不变输入重试受机械约束

- 状态: confirmed
- 来源: REQ-001

相同 phase、candidate、input 和 capsule 的新 evaluator 结果默认拒绝；显式理由至多放行一次，之后必须改变候选或评估输入。当前正式成功证据必须能定位到唯一通过收据。

## REQ-002 taskctl 二级帮助可以独立指导调用

- 状态: confirmed
- 来源: 用户要求“做 2”
- 关联: AC-003

每个 taskctl 子命令的 `--help` 应解释其参数职责、适用单位、关键默认行为以及 CAS、来源收据和分页快照等关系，不要求用户回读实现才能组成安全调用。

## AC-003 参数帮助完整

- 状态: confirmed
- 来源: REQ-002

所有子命令参数都有非空帮助；复杂的 context、completion-context 和 complete 提供最小示例，且帮助不改变现有命令或机器输出合同。

## REQ-003 已发布候选形成私有远端 Git 基线

- 状态: confirmed
- 来源: 用户要求“做 4”
- 关联: AC-004, CON-001

保留并整合当前 dirty 候选与本轮改进，形成职责清晰的本地提交，并非强制同步当前已配置上游。

## AC-004 Git 身份与同步可读回

- 状态: confirmed
- 来源: REQ-003

提交前验证实际差异和忽略范围；提交后 HEAD、当前分支和上游关系明确，非强制推送成功，工作区无未提交遗漏。

## CON-001 不再次发布 Codex

- 状态: confirmed
- 来源: 项目逐次发布授权合同与当前用户仅选择 1、2、4

本轮不运行 `Publish`。源码与真实 Codex 安装因 CLI 和开发门禁变化出现差异时如实记录，只读 `Status` 不创建发布授权。
