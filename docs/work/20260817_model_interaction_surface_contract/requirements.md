# 模型交互面合同：需求分析

## REQ-001 所有模型感知与修改内容都按交互面设计

- 状态: confirmed
- 来源: 用户明确指出命令返回、生成给模型阅读的文件和交给模型修改的文件都应纳入同一根本问题
- 关联: AC-001, AC-002, AC-003, UDES-001, UDES-002

任何会被模型直接读取、生成或修改的工具返回、文件、文档、日志、快照、索引、生成视图和恢复内容，都必须按模型当前判断或修改责任设计，不因它已经存在于文件系统、stdout、程序对象或传统工程格式中就默认适合作为模型交互内容。

## AC-001 交互面先确定事实 owner、消费者和当前责任

- 状态: confirmed
- 来源: REQ-001 对用户要求的原子化
- 关联: REQ-001

形成模型交互面前，先确定事实的权威 owner、模型是读取者还是修改者、当前要完成的判断或变更以及内容生命周期；存储位置、文件扩展名、调用位置和已有字段不能替代这些判断。

## AC-002 模型读取面只提供最小充分证据

- 状态: confirmed
- 来源: 用户要求模型直接阅读的内容采用极简设计
- 关联: REQ-001, AC-006

模型读取面只保留缺失后会改变当前判断、定位、动作、验证或恢复的信息；机器信封、正常默认值、重复事实、完整历史和大型原始内容默认留在上下文外，需要时通过稳定标识、精确位置或有界查询渐进取得。

## AC-003 模型修改面降低正确变更的整体负担

- 状态: confirmed
- 来源: 用户明确把交给模型修改的文件纳入相同原则
- 关联: REQ-001, REQ-002

由模型直接维护的长期内容应使同一职责、约束和验收关系局部可见，具有稳定、可定位且可验证的修改边界；生成内容、缓存、重复摘要和只供程序维护的字段不得迫使模型同步修改多个决定同一事实的位置。

## REQ-002 按消费者和生命周期保持唯一权威事实

- 状态: confirmed
- 来源: 用户要求模型内容极简而正常机器输出保持完整，并要求从根本而非表面格式解决
- 关联: AC-004, AC-005, UDES-002, UDES-003

同一事实同时服务模型、人和程序时，应按长期维护主体和生命周期确定唯一真源，再由正式 owner 提供适用的模型读取面、模型修改入口或机器表示；不得为方便某个消费者建立需要长期双向同步的第二真源。

## AC-004 模型或人维护的真源派生机器产物

- 状态: confirmed
- 来源: REQ-002 对唯一真源要求的原子化
- 关联: REQ-002

当模型或人类是长期语义维护者时，正式真源应支持可靠理解和局部修改，程序需要的索引、缓存、清单或生成视图从该真源可重建地产生；派生产物不得反向决定或要求重复维护原语义。

## AC-005 程序维护的真源通过投影或语义入口供模型使用

- 状态: confirmed
- 来源: REQ-002 对机器资产要求的原子化
- 关联: REQ-002

当程序拥有完整结构、日志、索引、快照或状态时，机器真源保持稳定完整；模型通过 owner 提供的有界投影、查询或受验证语义修改入口取得和改变必要信息，不默认整份读取或直接编辑机器表示。

## REQ-003 AgentBase 的当前正式交互资产接入统一合同

- 状态: confirmed
- 来源: 用户要求根据上述分析继续推进完善，而不是停留在口头原则或单一命令返回
- 关联: AC-006, AC-007, AC-008, UDES-003

AgentBase 应把模型交互面合同接入跨项目内核、项目维护规则、文档驱动交付资产、任务资产和当前有直接模型消费者的机器记录入口；上一版 taskctl/workctl 双视图继续作为工具输出子集，不被误标为已经覆盖文件读取与修改。

## AC-006 有界恢复在读取前规划而非事后统一截断

- 状态: confirmed
- 来源: 用户强调问题不限于格式，项目既有质量优先与渐进上下文要求
- 关联: REQ-001, REQ-003

预算和读取范围在证据选择前参与规划；不足时保留当前结论、异常、直接依据与精确恢复入口，并按语义单元续查。不得先展开完整工具对象或文件后统一裁字符串，也不得仅把 JSON 改写成其他格式冒充精炼。

## AC-007 当前文档和任务资产明确真源、生成物与修改入口

- 状态: confirmed
- 来源: REQ-003 对当前消费者的原子化
- 关联: REQ-003, AC-003, AC-004, AC-005

Delivery Workflow 与 Task Table Manager 的正式合同应明确哪些 Markdown 由模型维护、哪些 JSON 由程序消费、哪些索引与视图可重建，以及模型应通过哪个入口读取或修改；正式说明不得继续描述已经退出的默认输出或诱导模型编辑生成物。

## AC-008 真实模型消费入口验证读取与修改质量

- 状态: confirmed
- 来源: REQ-003 对完成证据的原子化
- 关联: REQ-003, CON-001

验证分别覆盖模型读取能否得到充分结论、模型修改能否局部作用于唯一真源、机器合同是否稳定、派生产物能否重建以及渐进恢复是否可定位；再比较完整调用链 Token。文件更短、格式改变、静态规则存在或单项测试通过都不能单独证明模型交互质量已经改善。

## CON-001 质量、Token、速度顺序不变

- 状态: confirmed
- 来源: 项目根需求与用户当前确认
- 关联: REQ-001, REQ-002, REQ-003

先保证需求、正确性、授权、安全、可维护性和完成证据；质量同等充分时才降低 Token，二者不退化时才优化速度。最短文本、最少文件或最低 Token 不能以隐藏必要关系和增加误改风险为代价。

## CON-002 不混入 source_snapshot 表示或插件迁移

- 状态: confirmed
- 来源: 用户此前明确要求本轮不混入 source_snapshot 压缩和插件迁移
- 关联: REQ-003

本版本不改变 source_snapshot 的事实表示、引用池或时效语义，也不改变当前 DirectCompatibility 分发模式。

## CON-003 Codex 发布仍需当次明确同意

- 状态: confirmed
- 来源: 用户明确要求任何再次发布到 Codex 都需针对当次发布同意
- 关联: REQ-003

开发、验证、Git 维护或此前发布授权均不能替代本版本向真实 Codex 根目录执行 Publish 的单独授权。
