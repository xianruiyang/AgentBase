# 模型交互面合同：用户设计

## UDES-001 模型直接感知或修改的内容统一纳入设计

- 状态: confirmed
- 来源: 用户明确补充“不单是命令的返回，包括生成跟模型阅读的文件，给模型修改的文件”
- 关联需求: REQ-001

命令返回、模型读取的生成文件以及交给模型修改的文件属于同一个根本问题，不能只优化 CLI stdout。

## UDES-002 模型面极简而机器面保持正常完整

- 状态: confirmed
- 来源: 用户持续确认模型直接阅读和修改的内容应极简，机械读取的正常输出应格式化且信息充分
- 关联需求: REQ-001, REQ-002

模型直接消费的内容按当前实际用途只保留必要信息；程序消费者继续获得结构稳定、字段充分并适合解析的表示。

## UDES-003 从内容 owner 解决而非依赖通用 hook 或格式器

- 状态: confirmed
- 来源: 用户明确主张由自己创建的工具针对模型或机械消费者分别设计输出，并质疑 hook 无法辨别语义
- 关联需求: REQ-002, REQ-003

决定哪些信息必要的逻辑属于实际内容 owner。全局 hook 不承担任意格式识别、通用摘要或领域裁剪；规则只改变模型的判断起点，具体读取与修改面由工具、文件或工作流 owner 实现。

## UDES-004 格式在必要信息确定后按真实成本选择

- 状态: confirmed
- 来源: 用户提出 YAML、TOML、HJSON 等低 Token 候选，并进一步指出问题不只是格式
- 关联需求: REQ-001, REQ-002

先删除不影响当前判断或修改的信息，再按真实 Token、可读性、可定位性和程序需求选择表示；不把某种格式名称当成自动优化证明。
