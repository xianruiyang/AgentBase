# AgentBase Evo 完成成本估算

本文件供用户安排实施时间与额度，实施模型据阶段实绩修订。估算日期为 2026-09-09，范围为 [SOL-011](solution.md#sol-011-接入步骤与兼容性) 的 M1—M5：把全部十三项需求实现为可使用、经必要验证的基础版。估算不是额度申请、运行授权或完成承诺。职责与验收仍归 design/solution；本文只维护成本假设、范围和失效条件。

## 估算口径

主代理按用户明确的 **GPT-6 Astra high** 估算，不采用“Sol 主力实现、Astra 少量审阅”的前提。总 Token 包括主代理、实施子代理、失败修复以及交付必需的小规模真实运行/模型评分；不假定委派便宜模型必然减少总成本。这里未更改任何线程或角色设置。

“完成”包含独立评分、自定义数据计算、七类组合、分组、并发排队、环境复用、全代理用量、动作追溯、人工介入、有限自动循环、兼容及使用文档。交付以后用 Evo 做持续优化、大规模样本研究、额外宿主适配和 Deploy/Release 不在工期内。必要的真实功能验证已计入，不能在开发估算之外再重复加一遍同批成本。

这是按方案工作包给出的**低置信度工程区间**，不是 Astra high 的历史实测预测。目前有既有 runner、用量收据和事件解析可复用，但没有覆盖 Evo 全链的 Astra high 开发样本。此前 Sol 单线程评测不能直接换算成本项目开发工时或 Astra 周额度；不通过付费跑题来制造估算精度。

## 工期与 Token

假设需求保持当前范围、现有基础可接入、一个主代理连续推进且只在稳定边界内有界委派；宿主采用当前约 16 逻辑线程/32 GiB 内存这一容量等级。真实运行初期按根作业并发 1，资源验证后简单场景可用 2；Provider 或重构建独占，不按 CPU 线程数推算可开多少模型。宿主繁忙导致的额外等待不包含在有效工时内。

| 阶段 | 有效推进时间 | 总 Token 预算 |
| --- | ---: | ---: |
| M1 离线评分核心 | 6—10 小时 | 6—12M |
| M2 可用评分版接入 | 10—18 小时 | 10—20M |
| M3 七类组件接齐 | 14—24 小时 | 18—34M |
| M4 自动迭代 | 8—14 小时 | 10—20M |
| M5 兼容、恢复与交付收敛 | 6—10 小时 | 6—14M |
| **完整 Evo 基础版** | **44—76 小时** | **50—100M** |

以上时间是整个实施任务的有效墙钟时间，不是所有并行代理时长求和；包括常规调试、本地检查和必要运行等待，不包含额度恢复、用户评审停留、外部服务故障和长期离线。按每天 8 小时推进，约 **6—10 个工作日**；排期可先按约 60 小时、75M Token 的区间中部占位，不能当作精确预测。

阶段区间来自工作量判断：M1 主要是数据合同与计算；M2 跨调度、恢复和真实运行；M3 有多种构建/宿主接口，当前未知最多；M4 复用已有评测链；M5 处理跨链反例和文档。代码生成通常不是主要等待，错误的运行身份、后代用量和恢复判定会造成返工。

总量中预留约 8—18M Token 用于必要的真实功能验证及其模型评分，其余约 42—82M 用于实现、审阅和修正；这只是预算分配，不是强制消耗。优先用合成数据和已有收据验证机械逻辑；首次真实闭环成立后才展开其余适用场景。若小场景已证明目标，不为花完预算增加重复。

中间的 M1+M2 约 16—28 小时、16—32M Token，只代表可用评分版，不代表用户所问的完整 Evo。

## “额度”的可计算与不可计算部分

总 Token 是输入与输出之和，缓存输入已在输入内，推理输出已在输出内，不再重复相加。缓存比例、上下文长度、真实输出与等待条件会显著改变账单和耗时；high 不对应一个可直接乘在所有任务上的固定倍数。

可按公开价格给出 Standard 档的 **Codex credits 等价预算**。2026-09-09 官方页面列 Astra 每百万普通输入/缓存输入/输出分别为 250/25/1250 credits；Astra Fast 为 Standard 的 2.5 倍。此处只选 Standard 作统一算例，不声明当前实际速度档位，也不改变它。[官方用量与价格说明](https://learn.chatgpt.com/docs/pricing)

令 I 为输入总量、K 为其中缓存输入、O 为输出量：

`credits = ((I - K) × 250 + K × 25 + O × 1250) / 1,000,000`

若暂按全部用量折算 Astra，假设输出占总 Token 的 2%—5%、缓存占输入的 80%—95%，50—100M Token 对应约 **3,000—13,000 Standard 等价 credits**。这些比例是预算假设，不是本机 Astra high 已测分布。实际使用不同角色模型时须按各自实际模型逐项结算；缓存更低、输出更多或使用 Fast 会超出该算例，不能将它当作账户扣费保证。

**Standard 等价 credits、套餐包含额度和重置券是不同单位。** 官方没有在上述价格表中承诺固定的套餐周 Token 数量，账户工具也没有提供可靠转换，不能由剩余百分比反推总容量。不在可提交文档保存账户余额、券身份、私人结果路径或即时剩余比例。

若采用用户提供的每周约 4,000M Sol Token 作为规划基准，可作条件换算：Standard 下 Astra 的普通输入、缓存输入和输出费率都为 Sol 的 2.5 倍（Sol 分别为 100/10/500 credits）。假设两者输入/缓存/输出构成相同，并以公开费率比例近似套餐额度消耗，则该基准约等价于 1,600M Astra Token；完成 Evo 的 50—100M 对应 **一个完整周额度的约 3.1%—6.3%**，中部 75M 约为 **4.7%**。若 Astra 使用 Fast、Sol 基准仍是 Standard，则约为 **7.8%—15.6%**。

这不是官方保证的 Pro 周容量，也不证明 Astra high 与该 Sol 基准有相同的缓存/输出构成；high 的影响已通过实际 Token 分布体现，不再额外套用一个虚构倍数。在上述假设成立且没有其他任务挤占额度时，完整周额度足够覆盖本估算，无需为 Evo 预留一次完整重置；工期仍按前述工作包估算，不按额度百分比缩短。

## 实施后的校准与重估

实施获授权后，先完成 M1 中有真实消费者的一段工作，记录对应主代理及后代的实际用量、工时和产出，按剩余工作包更新区间，不按代码行数线性外推。需要估算套餐消耗时，在无其他账户任务干扰、无跨重置且用户允许读取用量的有界阶段前后取差；百分比取整或窗口变化时只能给区间，不能伪装为精确 Token 配额。

下列事实出现时重估受影响阶段：实际宿主缺少必要事件/隔离能力；Provider 或 hook 必须更换接入设计；角色用量无法可靠归账；环境重置存在污染；评分计算需求超出当前设计；或首阶段 Astra 实际消耗明显落在假设之外。先解释差距与替代动作，不自动降需求、换模型、消耗重置券或增加真实评测规模。

本文由维护模型在假设或已证成本改变时局部更新；原始校准收据留本机。方案变化时按阶段重估，不把每轮进度追加成成本日志。
