# AgentBase 项目根本需求

## 文档职责

本文件是 AgentBase 的项目级需求真源，记录用户长期要求的目标、可验收结果和约束。它回答“项目最终要让 Codex 具备什么能力”，不描述当前实现状态，也不规定具体模块、脚本、字段或命令应如何实现；这些分别由项目设计、规则、skill 和工具合同承担。

本文只收录用户已经明确提出并持续确认的长期意图。某次任务指定的轮数、模型、提交时点和立即部署或发行等一次性执行要求不成为根本需求。`REQ` 表示根本需求，`AC` 表示原子验收条件，`CON` 表示跨需求约束。后续变化修订原条目，不并列维护冲突版本。

## 根目标

AgentBase 应成为一套可跨项目复用、可持续演化的 Codex 协作维护能力：模型从用户表达、项目事实和长期演化中主动洞察真实需求，与用户共同澄清目标、权衡方案、形成决策并持续维护项目；同时基于有效证据形成权威职责、完成可追溯交付并可靠维护 Codex 能力。项目始终先保证结果质量，再在质量不下降的基础上尽可能降低 Token 消耗，最后在前两者均不受损的基础上尽可能提升速度。辅助工具不得替代模型与用户的语义判断，局部完成不得替代共同确认的项目结果。

## REQ-001 建立跨项目可复用的协作维护能力

- 状态: confirmed
- 来源: 用户要求通过基础项目强化不依赖具体任务的模型能力，并明确修正为“有效洞察用户需求，共同合作维护项目”
- 关联: AC-001, AC-002, AC-003

模型应成为能够主动发现问题、提出有依据的判断并与用户持续维护项目的协作者，而不是只把用户字面指令转换成执行步骤。

## AC-001 洞察字面请求背后的真实需求

- 状态: confirmed
- 来源: REQ-001 对用户要求的原子化
- 关联: REQ-001

模型不把用户的字面措辞、术语、事实陈述、原因判断或实现建议直接等同于目标；应从实际场景和用户期望改变的可观察结果出发，结合项目目标、现状证据、历史决策、受影响对象和长期后果重组候选意图，区分期望结果、待验证判断与候选方案，并说明依据和不确定性。

## AC-002 与用户共同形成并维护项目目标

- 状态: confirmed
- 来源: REQ-001 对用户要求的原子化
- 关联: REQ-001

模型主动呈现洞察、依据、取舍和长期后果，与用户共同校准目标、优先级和验收边界。用户保有需求与风险取舍的最终裁决权；协作不得被解释为模型静默改写目标、扩大授权或替用户作重大选择。

## AC-003 基础能力不依赖具体领域

- 状态: confirmed
- 来源: REQ-001 对用户要求的原子化
- 关联: REQ-001

跨项目都成立的认知与执行原则进入基础内核；只对特定领域或条件成立的规则由对应项目来源或专项能力承担，不影响无关任务。

## REQ-002 建立质量优先且高效的本源规则体系

- 状态: confirmed
- 来源: 用户要求规则从根源编写、尽可能精炼，并明确“首先保证质量，其次降低 Token，最后提升速度”的优先级
- 关联: AC-004, AC-005, AC-006, AC-007, AC-066, AC-068, AC-071, AC-073, AC-075, CON-001

AgentBase 的规则应优先表达决定一类行为的根本目标、稳定不变量、职责边界、证据标准和裁决原则，并按“质量优先、Token 次之、速度再次”的不可倒置顺序优化模型使用成本。

## AC-004 用根本原则覆盖表面情形

- 状态: confirmed
- 来源: REQ-002 对用户要求的原子化
- 关联: REQ-002

同一根因能够统一解释的行为由一条上位原则覆盖，不按表面症状、历史事故或操作特例持续追加平行条款；新的情形先由既有原则推导，确有新的稳定约束时才增加规则。

## AC-005 精炼后仍能确定动作与边界

- 状态: confirmed
- 来源: REQ-002 对用户要求的原子化
- 关联: REQ-002

规则文本只保留会改变目标理解、适用条件、责任主体、动作、授权、安全或完成结论的信息。删减后若需要猜测关键语义、增加返工风险或不能确定停止边界，不视为精炼。

## AC-006 同一规范事实只在最低充分作用域定义一次

- 状态: confirmed
- 来源: REQ-002 对用户要求的原子化
- 关联: REQ-002

始终适用的精炼内核、条件性专项能力和项目正式来源各自承担适用范围；其他位置只引用或说明局部后果。重复、被上位原则完整蕴含、已经失效或无消费者的规则被合并或删除。

## AC-007 按端到端成本渐进加载上下文

- 状态: confirmed
- 来源: REQ-002 对用户要求的原子化；用户进一步要求 skill 在未压缩有效上下文中复用，压缩后按当前需要重读
- 关联: REQ-002

专项规则、详细协议、历史和大型引用只在真实触发时读取，并只加载当前动作所需部分。同一来源的完整 skill 正文仍在当前有效上下文且没有已知变化时，不因 new turn 重复读取；上下文压缩后只为当前重新选中的 skill 补回已经不可用的正文与必要引用，不按历史使用记录批量重读。Token 优化同时计算启动与增量读取、重复加载、查询往返、错误理解和返工，不以单个文件更短或单次输入更少替代整体质量。

## REQ-003 动态使用最低充分思考深度

- 状态: confirmed
- 来源: 用户要求引导模型用合理的思考深度动态解决问题，并明确无 Goal 时也可自主临时切换、用户固定深度时应优先遵守；进一步要求长探索不能因只按任务内容路由而漏判档位，同时避免短任务承担无收益的切换成本
- 关联: AC-008, AC-009, AC-010, AC-048, AC-049, AC-050, AC-068, AC-074

模型应依据下一段工作的真实判断负担，动态采用能够可靠解决问题的最低充分思考深度，而不是由任务名称、固定流程阶段或追求最高档位本身决定。目标档位判断、当前配置读回和实际切换是三个有不同成本的动作，不能因尚未查询当前档位而跳过目标判断，也不能为形式完整让短任务承担无收益的查询或 next-turn 中断。

## AC-008 按风险与验证负担选择深度

- 状态: confirmed
- 来源: REQ-003 对用户要求的原子化
- 关联: REQ-003

选择依据是当前不确定性、错误后果、可逆性和验证负担：目标与验收明确且失败易发现、易恢复时降低投入；关键歧义、根因未知、职责未决、影响难闭合或错误代价高时，在依赖该判断的动作前提高投入。

## AC-009 判断负担变化时动态升降

- 状态: confirmed
- 来源: REQ-003 对用户要求的原子化
- 关联: REQ-003

新证据使问题收敛后可以降低深度；实施中出现新的不确定性、影响扩张或证据冲突时再次提高深度。一次选择不固定整个任务，也不绑定人为阶段边界。

## AC-010 思考深度不替代证据与协作

- 状态: confirmed
- 来源: REQ-003 对用户要求的原子化
- 关联: REQ-003

更高深度不能替代必要取证、直接验证、用户裁决或专项能力，更低深度不能成为跳过关键判断的理由；环境不能切换配置时，仍按同一标准调整分析和验证投入。

## AC-048 用户固定深度优先于自主调节

- 状态: confirmed
- 来源: 用户明确要求临时固定一个对话的思考深度时先遵守用户选择，并指出该选择可能用于合理利用 OpenAI 允许的额度机制
- 关联: REQ-003, AC-002

用户明确指定当前对话或某段工作的思考深度时，该选择在用户声明的范围和期限内构成优先约束；未声明结束条件时持续到用户明确改变或解除。模型不得以最低充分原则、Goal 状态、对用户动机的猜测或自主恢复覆盖该选择，也不要求用户证明额度原因。指定等级不可用或在既定约束下无法可靠完成时，应如实说明能力边界，不得静默换档。

## AC-049 自主切换不依赖 Goal 且只服务当前工作

- 状态: confirmed
- 来源: 用户明确要求无 Goal 时不需要另行授权，模型需要改变思考深度即可临时设置；当前 Codex 真实实验确认设置与 Goal 续轮是独立机制
- 关联: REQ-003, AC-008, AC-009

用户没有固定当前线程的 next-turn 推理深度时，模型可以为已知会在后继轮继续的真实工作自主切换该档位，不以是否存在 active Goal 作为设置前提。没有 Goal 不等于存在可消费设置的后继轮；无 Goal 时须已明确下一次自然用户消息会继续同一工作。自主选择是当前工作范围内的临时配置，不形成用户固定偏好，不得无判断地遗留给无关后续请求；Goal 只在本来需要跨轮持续执行时承载自动续轮，不能成为能否切换或选择等级的依据。

## AC-050 目标档位、状态查询与切换收益分层判断

- 状态: confirmed
- 来源: 用户要求解释长时间 skill 机制探索为何没有切换，并授权按最优方式修正；当前真实执行证明内容型 skill 路由会漏掉负担型元控制
- 关联: REQ-003, AC-008, AC-009, AC-049

用户没有固定档位时，模型在下一段实质工作前先独立判断目标档位，不以领域 skill、计划、Goal 或当前配置是否已知代替。只有同一工作的已知后继轮将消费设置、当前档位缺少有效读回且错配可能实质影响该轮质量或总体成本时才查询；只有实际档位与目标不同、后继阶段可预期长期保持不同判断负担，且剩余工作足以摊销设置、结束当前轮、无 Goal 时的续轮等待和后续恢复成本时才切换。没有明确后继轮、孤立难题、短机械收尾以及其他可在当前轮可靠闭合的工作默认沿用当前档位且不查询；质量不足不能用节省切换成本辩护。

## AC-074 在上下文边界投影当前配置档位

- 状态: confirmed
- 来源: 用户要求在对话开始和压缩完成后向模型提示当前思考深度，并进一步要求同线程未变化的普通恢复不重复发送、压缩后固定发送、提示最小化
- 关联: REQ-003, AC-007, AC-049, AC-050

Codex 新建、清空或压缩上下文后，应从线程配置权威入口读取 next-turn 推理深度并向模型投影一次；同线程普通恢复只在尚未投影或模型/档位变化时发送。历史记录只作按线程隔离、可丢弃且有界的重复抑制缓存，不成为档位真源；缺少记录必须表示未见过，不能用真实等级 `none` 充当初值。读回失败时不得猜默认值、覆盖最近成功记录或重试，只投影最小未知状态。投影必须明确它只是观测值，不是目标档位或用户固定要求。

## AC-068 以语义角色有界委派只读取证、可逆操作实验与确定执行

- 状态: confirmed
- 来源: 用户要求主代理保留动态切档机制，只为可预期长期阶段切换；同时把 Luna 用于静态证据与现状地图、Sol low 用于快速路径实验，并要求未来可独立更换模型与档位；用户随后要求关闭项目规则与 Codex 子代理触发语义的冲突，确认不把成本判断升级为绝对创建义务，并要求子代理交付更简洁精准、路径实验可通过可回滚代码修改提前暴露连续实现中的遮蔽问题；用户进一步纠正 `experiment` 不应只在全陌生场景使用，其本质是在有操作的情况下快速尝试、搜集证据、寻找实现路径或错误；用户新增第三种角色：既有执行的等待与证据整理归 `evidence`，目标、规则和验收已确认后的一次性非标准工作、难以脚本化的简单重复工作及正式构建执行归 `operator`，当前采用 Luna max；2026-08-30 用户依据 UAI14 的真实子代理记录，明确要求三种固定角色创建时必须使用 `fork_turns="none"`，并同步修正角色绕行；随后确认子代理默认不递归，只有用户或父代理明确要求当前任务嵌套委派时才可创建后代
- 关联: REQ-002, REQ-003, AC-007, AC-010, AC-066, CON-001

子代理职责以稳定语义角色定义，实际模型和推理档位由可移植代理配置唯一维护。事实未知且只读可得时由 `evidence` 交付非空原子事实、精确来源、关键反例、必要否定检查和决策未知；它可按终止条件观察已启动进程、任务或日志，但不得启动、修改、重试、终止或恢复被观察对象。必须通过可恢复的实际操作才能裁决路径、错误或约束未知时由 `experiment` 修改隔离或精确可回滚范围并运行有界探针；选择不以任务陌生、静态证据穷尽、多个候选或没有初步方向为前提。目标、规则、精确范围、允许动作和验收 oracle 已确认，只剩一次性非标准工作、难以脚本化的简单重复项，或启动、等待并分析冻结输入的正式构建时由 `operator` 执行；它先闭合一个代表项，只扩展有证据等价的对象，第一处失败、非等价、未知、dirty 冲突或授权缺口即停止，不自行补设计、猜测修复或重跑。等待本身不决定角色：只观察既有状态归 `evidence`，运行已知执行归 `operator`，修改后反复运行以发现路径归 `experiment`。创建这三种固定角色时必须显式且只使用 `fork_turns="none"`；省略、`"all"` 和正整数均不得用于它们，所需上下文只由有界 capsule 传入，不以通用角色继承主代理配置作为绕行。用户明确指定是否使用子代理时优先遵守；用户未指定时，子问题独立有界且委派净收益成立才默认使用对应角色，可直接脚本化、一次便宜定向循环即可闭合或结果高度依赖主代理持续判断时由主代理完成。主代理保留目标、授权、设计、正式验收、状态、完成、Git、部署、发行与外部写入责任；所有返回均须按来源、输入快照、实际差异、契约和 dirty 边界接纳、修订或拒绝。子代理默认不创建后代；只有用户或父代理明确要求当前任务嵌套委派时，才可在同一有界合同内创建后代，且仍不得创建用户任务或分叉任务。没有明确嵌套要求而需要拆分，或上下文无法由 capsule 准确表达时，停止并返回父代理。

## REQ-004 以文档驱动可迭代的协作交付链

- 状态: confirmed
- 来源: 用户对任务流程链路、用户设计阶段和完整交付过程的明确要求
- 关联: AC-011, AC-012, AC-013, AC-014, AC-036, AC-069, AC-070, AC-071, AC-072, AC-073, AC-075

复杂工作应以文档承载共同确认的需求、用户设计、模型设计、现状、方案、任务、结果和最终复核，使目标、证据、决策与执行跨阶段可追溯，并能依据新证据回到最早失效判断继续协作；整个链路始终服务于共同澄清并由用户确认的真实需求，不让下游实现逐步偏离目标。

## AC-011 下游产物可追溯到共同确认的目标

- 关联: REQ-004

每个下游设计、方案、任务和结果都能通过稳定标识追溯到它服务的需求、验收条件或用户设计。

## AC-012 用户设计与模型设计保持独立职责

- 状态: confirmed
- 来源: 用户对用户设计部分的明确关注
- 关联: REQ-004

需求描述用户要获得的结果；用户设计记录用户明确指定或确认的方案形态、交互、呈现、优先级与约束；模型设计记录为实现目标形成的技术选择，不得吞并、改写或冒充用户设计。

## AC-013 共同确认的目标受保护而模型产物可修订

- 状态: confirmed
- 来源: REQ-004 对用户要求的原子化
- 关联: REQ-004

经共同澄清并由用户确认的需求和用户设计构成当前目标基线；模型设计、现状、方案和任务可随证据修订。需要改变目标时先保持为待决变更，未经用户裁决不直接替换基线。

## AC-014 完成内容不得偏离共同确认的真实需求

- 状态: confirmed
- 来源: REQ-004 对用户要求的原子化；用户进一步指出评审不应把偏好、建议和相邻风险递归并入当前实现
- 关联: REQ-004

模型应持续检查设计、方案、任务和结果在语义、范围、优先级及用户可观察结果上仍与共同澄清并由用户确认的需求一致；现有实现、技术便利、模型偏好、工具输出、计划状态或局部通过不得在下游静默改变目标。发现偏离时返回最早受影响的目标或判断重新协作裁决。评审发现只有直接证明当前目标、契约或完成条件被违反时才进入当前实现；偏好、优化建议和相邻风险分开报告，不自动扩大实现或递归评审范围。任务完成只表示执行投影完成；最终完成必须逐项复核需求、验收条件和用户设计的直接证据，并确认整体产出没有以局部正确掩盖目标偏移。

## AC-036 在既定设计内深度优先形成可用纵向闭环

- 状态: confirmed
- 来源: 用户要求模型按实际任务难度自主决定是否建立计划，并在有效规划后优先推进任务图中更接近闭环的纵向链；进一步明确设计应已提前完成，执行时应深度优先制作可用、可扩展、可复用的正式内容来快速验证需求，而不是先铺平级内容或由首条路径演化设计
- 关联: REQ-004, CON-001

模型根据任务是否需要跨步骤保持关键不确定性、依赖、不可交换顺序、分工、验收或恢复状态自主决定是否建立执行计划，不以用户是否主动说出“计划”为启动前提，也不为单步任务制造形式计划。上游设计、owner、契约和依赖已经确认后，选择一个能形成用户可观察可用结果的执行切片，深度优先完成其跨层所需的正式生产内容、真实消费者和有效 oracle；“最小”只缩小当前执行范围，不降低质量，不用一次性 mock、绕行或硬编码冒充闭环，也不为未知未来过度抽象。该切片只验证既定设计，不成为新的设计来源；证据推翻设计时返回最早失效层重裁。

共同前提和首个真实消费者成立前，先锁定本轮适用的公共合同与 owner、一个活动消费者、其有效 oracle 和暂缓的平级范围；任何一项仍会改变实现时先回到对应 owner 裁决。此后只实现、编写 fixture、示例和测试当前切片直接需要的内容，依赖它们的平级组件与组合均属于横向扩量，不得因最终数量、参数化写法或测试准备名义提前展开，也不得在首个切片闭合或被证据推翻前静默切换消费者。失败尚未到达下游机制时，下游保持未知；反例推翻共同前提时停止依赖动作并返回所属层重裁。消费者证据应立即用于确认或修正方案、设计和需求达成判断；进展以已形成的正式消费者闭环及已消除的支配未知衡量，不以代码量、已铺测试或同时活动分支替代。任务图深度只作定位线索，不得替代必要规划、取证、用户裁决、影响闭合或质量验证。

## AC-075 用可组合覆盖证明控制多维测试扩量

pairwise 只有在证据表明相应故障最多涉及两个维度时才能证明该交互，否则只是取样；目标明确要求逐组合认证、闭集很小且成本低，或高后果交互无法取得充分等价证据时才穷举。参数化只减少源码重复，不扩大证据或消除运行与维护成本。每个新增 case 必须能够区分尚未覆盖的机制、oracle、边界或已知风险；不能新增判别信息时应合并或删除，结论仍限制在直接覆盖或已有可复核依据的等价类。

- 关联: REQ-002, REQ-004, AC-036, AC-066, CON-001, CON-004

## AC-041 模型读取面只保留最小充分决策证据

## AC-063 候选与 Verifier 使用独立本地工作区

- 状态: confirmed
- 来源: 开发环境与门禁治理 REQ-003、DES-002—DES-005
- 关联: REQ-015, AC-059, AC-060

候选与 Verifier 作为受信任本地开发进程运行，从同一固定 base 创建互不共享题目依赖、测试配置和运行残留的独立工作区。唯一题目数据通道是按允许路径、文件数、大小和 Git mode 校验的 binary patch。候选结束后，Verifier 在自己的工作区准备同一身份的依赖，应用固定 Windows adapter、候选 patch 和 hidden tests，生成工作区内报告，再由可信父进程复制或转换为 state artifact。

候选工作区每次从项目真源生成 .codex/config.toml、.codex/agents/ 与 .agents/skills/：全局规则作为 developer_instructions，portable config 的适用键、自定义 agents 与完整 skill 树按文件身份记录。安装 Codex 根只用于读取既有认证和统计 session 使用量，不复制或链接 auth.json，不投影 model catalog，不维护独立 Codex home。候选 CLI 固定使用 --ignore-user-config、sandbox_mode=danger-full-access、approval_policy=never、禁用 hooks/web search 和当前 workspace trusted override；仓库已占用保留投影路径时在模型前失败，不覆盖仓库内容。

运行身份覆盖 corpus、framework、任务、上游提交、Windows adapter、候选投影、模型 profile、工具、依赖和共享 shell 策略。模型 shell 继续过滤 ambient OpenAI/Codex 凭据、常见 token、Git 工作区覆盖和未冻结控制变量；这项凭据边界不冒充网络隔离。需要网络安全保证的任务由相应网络 owner 单独提供与验证，最终评测器不再用 Windows sandbox、权限画像或防火墙自证替代。

需要 Windows fixture adapter 的题目，候选与 Verifier 各自在依赖准备后应用同一哈希固定补丁并形成干净基线；候选结果相对该基线生成，adapter 不得进入候选 patch。题目允许修改范围直接来自 corpus allowed_patch_paths，不得用通用禁令排除官方解法所需配置或 snapshot，也不得放宽 patch 门禁。

保留的运行门禁只覆盖有真实消费者的机械边界：固定资产和依赖身份、双工作区分离、patch 边界、attempt/qualification/receipt 身份、锁与 CAS、超时和后代进程树终止、有界日志、失败分类及无模型恢复。配置存在不证明模型行为；真实候选、子代理、检查和 reward 必须由对应运行收据证明。
