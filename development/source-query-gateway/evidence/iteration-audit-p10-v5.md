## 可观察机制

- 五个 run 在普通首次文本查询前加载了 `source-query/SKILL.md`；HJSON 第一次还同时预加载 `rg-fd.md` 和 `lsp.md`。agent 的可见说明明确把已知限定符号位置全集误判为“符号身份与引用流程”，不是项目规则要求。
- 唯一未加载 skill 的 containing run 先执行 `srcq rg --help`。两类行为都说明上一版精简删除了“普通调用不预加载高级 skill/help/doctor”的稳定非触发边界。
- 39 次命令产生 108,310 个工具 stdout 字符；四个工具结果仍出现 `@more`，五个出现 `@cut`。containing 在定位正式实现后继续分段读取整个文件或追查 fingerprint 上游；HJSON 的项目入口与 §8/§8.1 读取属于真实项目成本，但 skill/LSP 预载、广域首查和 machine full 复核不属于项目要求。
- 本轮 8192 estimated-Token 单文件自动闭环没有覆盖这些高成本链路：首次 locator 多为多文件结果，文件确定后模型改用直接 `Get-Content`。因此这批数据不能证明放大单页有效；它也不是本轮总成本上升的直接原因。无真实收益证据时不应保留更高默认页预算。

## 下一裁决

1. `source-query` 收窄为已经出现分页/截断、明确 AST 或文本后仍有真实身份歧义的专项 skill；普通定义、调用、限定符号全集和显式映射不触发。
2. 全局一条规则恢复稳定的非触发边界：普通查询不先加载高级查询 skill、help、doctor 或 capabilities。它不规定锚点组合、调用次数或阅读顺序。
3. srcq 只在完整结果按现有 2048 estimated-Token 预算即可容纳时越过初始 80 项限制；可在同一总预算内提高单行完整度，但不再把单文件默认预算放大到 8192。
4. 形成新机制后才运行下一批 6-run；本身份不重跑，不进入 12-run。
